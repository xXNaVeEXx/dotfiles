# linux-gui-computer-use

# GUI-Anwendungen auf dem Linux-Desktop des Nutzers fernsteuern (Handtests ohne Nutzer)

Use when the user asks to run GUI handtests / control the computer yourself (start app, click, type, read screen) on their Linux machine — Wayland session with XWayland, no system-wide installs allowed (Nix only).

## Verfahren

1. **Voraussetzungen prüfen:** `echo $XDG_SESSION_TYPE $DISPLAY $WAYLAND_DISPLAY`, `xauth list` (Cookie für `:0` nötig). Vorhanden: ImageMagick `import`, `tesseract`, `ffmpeg`. Fehlen typischerweise: `xdotool`, `xwininfo`, `playerctl` — nie systemweit installieren, sondern pro Lauf: `nix shell nixpkgs#xdotool nixpkgs#xwininfo -c '…'`.
2. **App unter XWayland zwingen** (xdotool wirkt nur auf X11-Fenster): `GDK_BACKEND=x11` plus für Tauri/WebKitGTK stabile Software-Sicht: `WEBKIT_DISABLE_COMPOSITING_MODE=1 WEBKIT_DISABLE_DMABUF_RENDERER=1 LIBGL_ALWAYS_SOFTWARE=1 NO_AT_BRIDGE=1`.
3. **Isoliert + RAM-begrenzt starten:** eigene Datenordnung der App nutzen, falls vorhanden (z. B. `LUMI_HOME=…` mit vorgefertigten JSON-Dateien: Einrichtung erledigt, Offline-Modus), sonst `XDG_DATA_HOME`/`XDG_CONFIG_HOME` umleiten. Start: `systemd-run --user --scope -q -p MemoryMax=3G … app > .tmp/…/app.log 2>&1 &` — Log auf Platte (`.tmp/`), RAM-Regeln des Rechners beachten (ein schwerer Schritt, vorher `free -m`).
4. **Wayland-Fokus holen — vor JEDER Interaktion:** XTest-Klicks/Tasten wirken nur, wenn der Wayland-Compositor (KWin) das Fenster wirklich fokussiert hat; `xdotool windowactivate` täuscht nur den X-Fokus vor und Klicks landen dann still woanders. Fix: `kdotool windowactivate '{uuid}'` (UUID via `kdotool search --name "<Fenstertitel>"`, `nix shell nixpkgs#kdotool -c …`, `{}`-Klammern strippen). Treiber-Skript mit Helfern: `ht_activate` (kdotool-Aktivierung), `ht_click` (activate → sleep → mousemove --window → click, GETRENNTE Aufrufe — kombinierter Aufruf warpt nicht), `ht_shot`, `ht_type`. Fenster-ID via `xdotool search --onlyvisible --class <klasse>`; Text `xdotool type --delay 60`; Tasten `xdotool key ctrl+k` (wirken global, nicht `--window`).
4b. **Hyprland-Desktop (Omarchy): native Wayland-Fenster ohne XWayland steuern:** Geometrie/Klasse/Titel aus `hyprctl clients -j` (die `at`/`size`-Werte sind logische Koordinaten und gelten 1:1 auch bei `scale: 2`), Region per `nix shell nixpkgs#grim -c grim -g "x,y WxH" shot.png`, Auswertung mit dem read-Tool (Vision). Grenze: grim fotografiert den Output-Framebuffer — verdeckte oder nicht angezeigte Fenster sind NICHT sichtbar; erst den Workspace aktiv schalten. Fokus/Workspace-Schalten: seit ~Hyprland 0.56 baut die klassische `hyprctl dispatch <dsp> <arg>`-Syntax ungültiges Lua ("expected a dispatcher …") und schlägt fehl (auch "')' expected near …"). Die neue Form ist Lua, z. B. `hyprctl dispatch 'hl.dsp.window.close({ window = "address:0x…" })'` (Antwort `ok`, Wirkung per `hyprctl clients -j` prüfen); weitere Dispatcher-Namen per `grep -rhoE 'hl\.dsp\.[a-z_.]+' ~/.local/share/omarchy ~/.config/hypr | sort -u`. `hyprctl eval` druckt nur `ok` ohne Rückgabewerte. Zuverlässiger Trick: ein Testfenster mit eigener `--class` starten — jedes frische Fenster stiehlt den Fokus und macht seinen Workspace aktiv; danach Geometrie aus `hyprctl clients -j` ziehen und grim-en. `hyprctl decorations '<class-regex>'` listet die Compositor-Dekorationen am Fenster (Shadow/Border/Glow) — trennt sauber, ob eine Titelleiste vom Compositor oder von der App selbst (CSD) gezeichnet wird. **KDE/KWin-Rechner remote (ssh):** Befehle der Nutzersession (nix, spectacle, kdotool, gdbus) haben über blankes ssh kein PATH/Session-Bus — sie per `systemd-run --user --pipe --quiet bash -lc '…'` in die Nutzersession hängen. Fenster inventarisieren/aktivieren mit `kdotool search --name .` / `getwindowname` / `getwindowgeometry` / `windowactivate '{uuid}'` (UUIDs in geschweiften Klammern), Screenshot per `spectacle -b -n -o /tmp/shot.png`; Geometrien sind logisch — bei scale 2 in physische Pixel umrechnen.
4c. **Nicht reproduzierbare Nutzer-Meldungen live abfangen:** Meldet der Nutzer einen Zustand („neues Fenster hat oben einen Balken"), den jeder eigene Repro-Pfad sauber zeigt: nicht weiter raten, sondern Watcher-Skript via bg_run starten (~3 min Laufzeit), das `hyprctl clients -j` alle 0,5 s pollt; bei NEUER Fensteradresse der Zielklasse sofort Client-JSON (class, initialClass, pid, xwayland, floating, decoration_mode, workspace) plus `/proc/<pid>/cmdline` und `environ` (WEZTERM-/XDG-/HOME-/DISPLAY-/WAYLAND-Schlüssel) loggen und Top-Streifen-Screenshots t0 (+0,2 s) und t1 (+2,5 s) schießen — so werden auch transiente Balken beim Fensteröffnen erfasst. Danach den Nutzer auffordern, JETZT seinen normalen Öffnen-Weg zu triggern, und den Turn beenden; der Watcher fängt den Zustand im Akt. Mux-Terminals (wezterm `start` ohne `--always-new-process` verbindet mit der existierenden GUI-Instanz): neue Fenster gehören dem ERSTEN GUI-Prozess, dessen cmdline/environ sagt nichts über den späteren Launch-Pfad — deshalb muss der Watcher jede Neuerscheinung selbst protokollieren, nicht nur den Startprozess inspizieren. Vor Watcher-Start die SEEN-Map mit den bereits existierenden Fenstern der Zielklasse befüllen und alte Shots leeren, damit nur wirklich NEUE Fenster feuern.
4d. **Handy-App-Handtests (Android-Emulator auf einem x86_64-Zweitrechner mit KVM, gesteuert per ssh/adb):** Emulator in einem Docker-Container (Präfix `lumi-test-…`, adb nur auf 127.0.0.1 binden), arm64-only-APKs laufen im x86_64-Image (API ≥ 30 google_apis) per eingebauter ARM-Übersetzung. Die Gegenseite (Desktop-App, Server, Zentrale) auf DEMSELBEN Host wie den Emulator starten (x86_64-Build, Xvfb) — der Emulator erreicht den Host als `10.0.2.2`; Server auf dem eigenen Rechner sind hinter dessen Firewall meist gesperrt, und ohne sudo kann man keine Ports freigeben (Alternative: `ssh -R` + `adb reverse`). Langläufer auf dem Zweitrechner per `systemd-run --user --unit=<präfix>-job-<name>` starten, wenn dort `KillUserProcesses` an ist (nohup-Prozesse sterben sonst beim ssh-Logout). Flutter-Texte stehen im `uiautomator dump` in `content-desc`, nicht in `text`; Tippen per `input tap` mit Koordinaten aus `bounds`. Netzwechsel per `svc wifi|data enable/disable` bzw. `cmd connectivity airplane-mode`. Wird der Quellbaum in einen Build-Container gespiegelt: Nix-Store-Shebangs (z. B. `gradlew`) im Spiegel auf `/bin/bash` umschreiben und root-eigene Ausgaben per trap `chown -R <uid>` zurückgeben.
5. **Textfelder in WebViews per JS statt Maus:** Eingabefelder (Composer, Konsole embedded UIs) nehmen XTest-Klick-Fokus NICHT zuverlässig an, Buttons/Sidebar schon. Route: DevTools-Konsole öffnen und React/DOM direkt steuern — Dropdowns/Knöpfe per `element.click()` (JS-Klick wirkt immer, Pixel-Klick ist Lotterie), React-Inputs per nativem value-Setter + `input`-Event + Enter-`keydown`. DevTools (Strg+Shift+I) öffnet nur FRISCH nach App-Start UND in der richtigen Ansicht; nach DevTools-Gebrauch grabt sich auch Strg+K ab → App neu starten. Code in die Konsole: kleine JS-Datei per Clipboard (xclip + Strg+V nach Klick in den Prompt) oder `eval(atob('<base64>'))`; `xdotool type` und Clipboard-Paste verstümmeln langen Klartext-Code.
6. **Fenster in den Monitor zwingen:** nach JEDEM App-Start `xdotool windowsize <id> 1280 700` — ein 820px-Fenster auf einem 720p-Monitor hängt unten über den Rand, Klickziele dort schlagen still fehl.
7. **Lesen:** Screenshot nur des App-Fensters `import -window <id> shot.png`, dann mit dem read-Tool (Vision) auswerten — deutlich verlässlicher als tesseract (dessen tessdata oft fehlt). Elementkoordinaten aus PIL-Zeilen-/Spaltenprofilen (Grauwert-Schwellen, Segment-Cluster) gewinnen; OCR nur als Fallback. Kleine UI-Regionen (Statusbar-Streifen, einzelne Widget-Texte) vor dem Vision-Lesen mit PIL exakt croppen und 2–3× hochskalieren — Ganze-Leisten-/Vollbild-Lesungen verwechseln Prozentwerte und Glyphen, weil die Texte dabei zu stark herunterskaliert werden; transiente Overlays (Panels) in einer Befehlskette öffnen → kurz warten → Screenshot, sonst ist das Overlay beim Read schon wieder zu.
8. **Prozess-Seite beobachten:** App-Log + Log-Ordner der App-Datenordnung tailen, Kindprozesse (z. B. Node-Hosts) per `pgrep -f` finden — Verhalten oft leichter am Log/Prozess belegbar als am Pixel. Achtung: Einstellungen der App können TROTZ isoliertem Datenordner ins echte Nutzer-Home laufen (z. B. Agent-Settings aus `$HOME/.pi/…`) — prüfen, welche Datei wo landet, bevor man Zustände wundern lässt.
9. **Dokumentieren:** je Handtest Screenshot + Vision-Lesung + Log-Auszug + Ergebnis in einen Bericht (Konvention des Projekts, z. B. `docs/reports/`), Checkliste erst nach Belag abhaken.

## Stolperfallen

- Nie den echten Schlüsselbund des Nutzers benutzen: App und Testläufe mit privatem Bus UND eigenen Daten- und Laufzeitordnern starten (`T=$(mktemp -d); mkdir -p "$T/data" "$T/run"; chmod 700 "$T/run"; XDG_DATA_HOME="$T/data" XDG_RUNTIME_DIR="$T/run" dbus-run-session --config-file=/usr/share/dbus-1/session.conf -- sh -c 'echo | gnome-keyring-daemon --unlock --components=secrets >/dev/null; <app>'`; ohne eigenes XDG_DATA_HOME legt der Test-Daemon `~/.local/share/keyrings/login.keyring` an, die der echte Daemon als gesperrte Collection „login“ übernimmt – danach fragt gh ohne GH_TOKEN bei jedem Aufruf per Entsperr-Dialog) oder einen Datei-Speicher der App erzwingen, und Handtest-Worker-Briefe das ausdrücklich vorgeben lassen. Grund: Ein Zugriff auf den gesperrten Login-Schlüsselbund öffnet einen Entsperr-Dialog mit dem Nutzerpasswort; bis er geschlossen ist, hängen alle anderen Secret-Service-Nutzer (gh, git-credential). Hängt er schon: Dialog nicht anfassen, Token aus dem entsperrten Default-Bund holen (`[ -n "${GH_TOKEN:-}" ] || GH_TOKEN=$(timeout 10 secret-tool lookup service gh:github.com); export GH_TOKEN` – nie einen geerbten Token mit einem womöglich leeren Wert überschreiben, weil gh sonst selbst den gesperrten Bund fragt) und Netzbefehle mit `timeout` laufen lassen. Ohne eigenes XDG_RUNTIME_DIR ersetzt der Test-Daemon zudem den Steuer-Socket `/run/user/<uid>/keyring/control` der Sitzung und löscht ihn beim Beenden. `--config-file` braucht das `dbus-run-session` aus Nix-Umgebungen (devShell): Es sucht `/etc/dbus-1/session.conf` und bricht sonst mit „Failed to open "/etc/dbus-1/session.conf"“ und Exit 127 ab; unter NixOS die Option weglassen, in Containern ohne die Datei das Testbinary auf dem Host ausführen. `mktemp -d` innerhalb `nix develop` landet unter `/tmp/nix-shell.*/` (TMPDIR) und bleibt dort liegen: `T` im Rezept ausgeben und danach gezielt löschen. Kommt der Dialog immer wieder: in `~/.local/share/keyrings/` nach einer unerwarteten `login.keyring` suchen und ihre Geburtszeit (`stat`) gegen Testläufe halten. Ist sie leer und von einem Test angelegt, in einen Nebenordner verschieben statt löschen (umkehrbar), dann prüfen: `busctl --user call org.freedesktop.secrets /org/freedesktop/secrets org.freedesktop.Secret.Service ReadAlias s login` liefert `o "/"`, und `env -u GH_TOKEN timeout 20 gh auth status` läuft ohne Dialog. Erst danach den offenen Dialog schließen; nie ein Passwort eingeben. Fehlt danach `/run/user/<uid>/keyring/control`: `gnome-keyring-daemon.socket`/`.service` nicht neu starten (kann den Bund sperren und Entsperr-Dialoge in allen Apps auslösen); der Socket kommt mit dem nächsten Login zurück. Bis dahin können kurzlebige zweite `gnome-keyring-daemon`-Prozesse (D-Bus-/Portal-Aktivierung) auftauchen; harmlos, solange `~/.local/share/keyrings` unverändert bleibt und `busctl --user list | grep secrets` weiter den Sitzungs-Daemon zeigt.
- Wayland-Nativfenster sind für xdotool unsichtbar — ohne `GDK_BACKEND=x11` (GTK) bzw. X11-Backend der App scheitert die Steuerung still.
- Es ist der LIVE-Desktop des Nutzers: nur das Zielfenster aktivieren/fokussieren/anklicken, Screenshots nur fensterbezogen (`import -window`), nie Vollbild — sonst liest man private Inhalte und klickt fremde Fenster.
- Nach Rechner-Neustart ( Stromausfall) erst Maschine prüfen (`free -m`, `uptime`, `git status`) bevor schwere Läufe starten; Hintergrund-Wächter des Nutzers (systemd-oomd, ram-watch) killen bei Swap-Druck die größte Gruppe — App-Binaries mit `MemoryMax`-Scope starten.
- OCR-Strings der UI vorher aus dem Quelltext/i18n-Dateien holen (exakte erwartete Texte), statt OCR-Output frei zu interpretieren — tesseract verhunzt deutsche Umlaute gern; mehrere akzeptierte Schreibweisen prüfen. Lieber Vision (read-Tool auf Screenshot) + PIL-Profile als tesseract ohne tessdata.
- AT-SPI exportiert bei WebKit/GTK-Hybriden oft nur den GTK-Teil (Menüleiste), nicht das Web-DOM — für Web-Inhalte unbrauchbar, direkt die DevTools-JS-Route nehmen.
- Sound-Tests: WebKitGTK-Apps brauchen `ALSA_PLUGIN_DIR=<pipewire-nix-store>/lib/alsa-lib` (Fehler „libasound_module_pcm_pipewire.so"), danach App neu starten.
- `nix shell` lädt Kanal-Auspacken beim ersten Aufruf (Minuten) — Treiber-Skript so schreiben, dass EIN `nix shell … -c` alle xdotool-Aufrufe bündelt oder die Shell offen hält.
- `pgrep -f '<muster>'` matcht die EIGENE `bash -c`-Kommandozeile — ein folgendes `kill` ermordet die eigene Shell (Exit 143, Rest der Befehlskette läuft nie). Prozesse stattdessen per exaktem Namen ohne `-f` suchen (`pgrep -a <procname>`), per `grep -v` die Hauptinstanz/das Eigene ausschließen und nur die angezeigten PIDs killen. Nie nach allgemeinem Namen oder Nutzer killen (`pkill -x sleep`, `pkill -u <user> …`): Das trifft Wache-, Watchdog- und Aufsichts-Loops anderer Sitzungen desselben Nutzers. Eigene Hilfsprozesse nur über die gemerkte PID oder `pkill -P <eigene-pid>` beenden.
- Ein „Balken mit Knöpfen" oben in einem Terminal ist oft die EIGENE UI der App (TUI-Header, Tab-Leiste), nicht die Fenstertitelleiste des Compositors — zuerst den obersten ~60–90-px-Streifen separat croppen und 2× hochskalieren und prüfen, ob der Balken INNERHALB des Fensterinhalts liegt, bevor man eine Dekoration des Compositors vermutet.
- **Nutzer-Screenshot ≠ eigener Framebuffer → erst den Rechner identifizieren:** Sitz der Session und physischer Blick des Nutzers können auseinanderliegen (Remote-Bridge/SSH-Attach auf zweiter Maschine). Wenn der Nutzer etwas sieht, das der eigene grim-Screenshot nachweislich nicht zeigt: Tray-/Bar-Fingerprints vergleichen (Icons links/rechts, Uhrzeit-Text, Akzentfarbe der Bar-Unterkante) statt endlos lokal zu reproduzieren; passt der Fingerprint nicht, diag­nos­ti­z­ieren, WO der Nutzer wirklich sitzt (Fensterliste des Verdachtsrechners per kdotool/hyprctl über ssh), und dort fixen.
- Terminal-Emulatoren mit Wayland-SSD-Anfrage (xdg-decoration, z. B. WezTerm-Nightly) bekommen unter KDE/KWin eine echte Compositor-Titelleiste mit X/Maximieren-Buttons gezeichnet — `window_decorations="RESIZE"` der Terminal-Config ändert daran nichts, weil der Compositor entscheidet; Tiling-WMs (Hyprland) dekorieren nie (gleiche Config, anderes Verhalten je Desktop). Fix unter KDE: Fensterregel per `kwriteconfig6 --file kwinrulesc --group 1 --key noborder true` (+ `noborderrule 3`, `wmclassmatch 1`, Group General count 1) und `gdbus call --session --dest org.kde.KWin --object-path /KWin --method org.kde.KWin.reconfigure`; wirkt sofort auch auf bestehende Fenster.
- Gegenfall Hyprland: Ohne SSD zeichnet WezTerm (auch stable 20260716) bei `window_decorations="RESIZE"` einen EIGENEN CSD-Streifen ÜBER dem Fensterinhalt (dezente min/max-Glyphen oben rechts, ~10 px, mit laufendem GUI-Prozess auch in neu gespawnte mux-Fenster) — sieht aus wie eine Mini-Titelleiste. Fix: `window_decorations="NONE"` (RESIZE-Funktion bleibt über SUPER+Drag des Tiling-WM). Beweis-Test: Testfenster mit abgewandelter Config (`WEZTERM_CONFIG_FILE=/tmp/test.lua wezterm-gui start --always-new-process`, bg-Farbe als Fingerprint) und Top-Streifen-Zeilenprofil gegen ein Normalfenster. Vorhandene Fenster behalten den Streifen bis zum Neustart ihrer GUI-Instanz.
- Layer-Zerlegung bei „Balken oben": nacheinander (a) Bar/Panel per Toggle verbergen und schauen was bleibt (Achtung invertierte Semantik — Bar-Verstecken-Flag statt Anzeigen), (b) leeren Workspace fotografieren (Bande weg = fenster-gebunden), (c) `hyprctl decorations` + `hyprctl getoption general:col.active_border` (Bord-Farben = Theme, z. B. Salmon-Gradient) und Glow/Shadow vom Compositor von App-CSD trennen. Graue Vollbreiten-Bande direkt über Fensterinhalt + kleine helle Glyphen = Client-CSD; schmale farbige Linie am Fensterrand = Compositor-Border (normal, gewollt).
- Testfenster-Reste sauber beenden: eigenes Timeout mitgeben (z. B. `wezterm … start -- sleep 10`), Hauptprozess der App vorher per `pgrep -a` identifizieren und vom Aufräumen ausnehmen — sonst killt man dem Nutzer die laufende Instanz weg. Mux-Terminals (wezterm) selektiv aufräumen per `wezterm cli list --format json` (Felder window_id/pane_id/title/cwd) + `wezterm cli kill-pane --pane-id <N>` — `kill-window` existiert je Version nicht, Panes sind die stabile Adresse.
- Binary-Alter prüfen: `ls -l binary` vs. letzte Quelländerung (`git log -1 --format=%cd -- <src>`), sonst testet man einen alten Stand. Binaries aus einem geteilten Build-Ordner (Remote-Spiegel, gemeinsames `target/`) können aus einem anderen Branch oder Worktree stammen: Für Abnahmen das CI-Artefakt (z. B. AppImage) oder einen frischen Build vom Ziel-Commit nehmen und Commit plus Binary-Pfad in den Bericht schreiben. Neu bauen: inkrementeller Rebuild über das RAM-sichere Buildskript des Projekts im Hintergrund.
- Plötzliche „No such file or directory"-Phantome auf eigentlich vorhandene Pfade (~/projects & Co. „weg", Minuten später wieder da, alte mtimes): KEIN Datenverlust — erst `journalctl --since` auf Suspend/Sleep prüfen (Sleep-Taste/Deckel friert user.slice und deaktiviert Mounts; Agent-Shells, die während des Freeze laufen, sehen halb eingefrorene Zustände). Nach dem Resume alles neu verifizieren statt Katastrophen-Diagnose (rm-Verdacht, Trash-Suche) zu fahren.

## Eskalation

Klappt die Steuerung nicht (kein X11-Backend möglich, native Wayland-only App), ofere der Nutzer kein Einlenken: dann Pi-Extension „computer use" bauen (Screenshot via GNOME-Shell-D-Bus-Screenshot-API oder Portal, Eingabe via ydotool/libei) — nur auf ausdrücklichen Auftrag, wie vom Nutzer formuliert.
