# mag-tech-release

Klasse: Eine Fassung einer App im mag-tech-monorepo veröffentlichen — von der Changelog-Kuration bis zum verifizierten GitHub-Release.

Verbindliche Repo-Regeln: `docs/rules/versionierung-und-releases.md` (Tag `<app>/vX.Y.Z`, Semver > letzter Tag DIESER App, Changelog-Abschnitt Pflicht, `latest` bewegt sich NICHT) und `docs/rules/encoding-deutsche-texte.md`. Merge-Mechanik (Checks, --admin, Synchronize, Watcher): Skill gh-pr-automation.

## Ablauf (Reihenfolge einhalten)

1. **Bestand aufnehmen:** `git fetch origin`; `git log --oneline <app>/vLAST..origin/main` (das kommt in die Fassung), offene PRs (`gh pr list`), Divergenz `git rev-list --left-right --count origin/main...origin/test`. Nur was auf main gelandet ist, wird released. **Abhängige Komponenten mit eigenem Tag prüfen:** Das KI-Gateway aishop (`apps/aishop`, Tag `aishop/vX.Y.Z`, eigenes `apps/aishop/CHANGELOG.md`) läuft getrennt; Kundeninstanzen ohne `PLATFORM_AI_PROVIDER` gehen über aishop. Vor jeder App-Fassung `git log --oneline aishop/vLAST..origin/main -- apps/aishop` lesen: Sendet die App etwas, das erst eine unveröffentlichte aishop-Änderung auswertet (z. B. eine neue Kopfzeile für das Denk-Level), wirkt diese App-Funktion beim Kunden nicht, bis aishop ausgeliefert ist. Dann die aishop-Fassung als Voraussetzung mit eigener Nummernfrage in den Release-Plan aufnehmen und dem Nutzer in einem Satz sagen, welche Funktion ohne sie wirkungslos bleibt. Grund: Sonst empfiehlt man dem Kunden eine Einstellung, die in Produktion still ignoriert wird. **Die Fassungsnummer legt der Inhaber fest:** Vor Issue, Changelog-Überschrift und PR-Titeln die Nummer erfragen (einen Vorschlag mit Begründung nennen), nie selbst nach Semver-Gefühl wählen. Grund: Eine eigenmächtige Nummer muss per weiterer PR-Kette test → main samt main-Build zurückgenommen werden. Auch den Zeitpunkt bestimmt er: Auf `test` arbeiten weitere Entwickler, die vor einem App-Release noch Fehler beheben oder Funktionen und Design selbst durchsehen wollen. Ein vorbereiteter Changelog-Abschnitt auf main und ein grüner main-Build sind keine Freigabe. Den Abschnitt vor dem späteren Tag um die inzwischen gemergten Änderungen ergänzen. Ein Release einer anderen App (z. B. aishop) braucht trotzdem test→main; das nimmt den aktuellen test-Stand mit nach main, liefert davon aber nichts aus.
2. **Changelog-Entwurf:** `npm run changelog:entwurf -- --version X.Y.Z` — AUF main ausführen (auf Release-Branches ist der Range leer, weil der letzte Tag auf main liegt). Der Entwurf listet Commit-Subjects; für Anwender-Texte die Commit-BODIES der Feature-Commits lesen (`git log -1 --format='%B' <sha>`) — dort stehen MAG-Nummern, Ausmaß („123 Stellen") und Beweggründe.
3. **Kuratieren:** Abschnitt `## vX.Y.Z — YYYY-MM-DD` vor den letzten Abschnitt in CHANGELOG.md. Stil wie bestehende Abschnitte: kurze Intro-Zeilen mit Spiegelstrichen, `### ⭐ Neu` / `### 🐛 Behoben`, Sie-Form, deutsche Anführungszeichen „…", **Fett-Titel** + eingerückte Unterpunkte, ein Satz pro Eintrag was der Anwender jetzt TUN kann — keine Internas, keine MAG-Nummern im Text. Der Abschnitt wird 1:1 der Body des GitHub-Releases (Quelle für den Auslieferungshelfer-Import; dessen Import-Sektionen: ⭐→funktion, ⚙️→anpassung, 🐛/🔒→fehlerbehebung, 🔧 Betrieb wird NICHT importiert).
4. **Notes-PR:** Branch `release-X.Y.Z-changelog` von main; Commit-Nachricht per Datei (`git commit -F`, echte Umlaute!), Nachricht „MAG-<n>: Release Notes für vX.Y.Z". **Vor jedem Push:** `python3 scripts/encoding-pruefung.py origin/test && git push …` mit && ketten (Commits mit ASCII-Umschriften wie „gruen" fallen sonst erst in der CI auf; Heilung braucht amend + Force-Push, Refspec `git push origin +<branch>`). PR → test, Titel = Commit-Nachricht. Changelog-only-PRs werden von build.yml legitim übersprungen; encoding/titel/waechter laufen.
5. **Freigabe-PR:** test→main, Titel „MAG-<n>: test nach main — Release Notes vX.Y.Z" (ohne Release: „MAG-<n>: test nach main — <Inhalt>“, Issue dafür anlegen). Stand laut Inhaber: Alle Kunden stehen auf eigenen Kanal-Tags (`DEPLOY_TAG=kunde-…`); ein main-Merge liefert an niemanden aus, ausgeliefert wird erst über Release-Tag bzw. Auslieferungshelfer. Der main-Zweig-Bau in `.github/workflows/build.yml` veröffentlicht trotzdem noch `latest` (`pubtags=… latest`, Übergangskommentar). Nur wenn ein Kunde mit `DEPLOY_TAG=latest` neu dazukommt (Kunden-`conf`, `install-customer-cluster.sh`), liefert der Merge bei ihm sofort aus; dann vorher fragen. Läuft test voraus: direkt Checks + merge (gh-pr-automation: Head-SHA verifizieren, --admin bei toten Kontexten). Läuft main voraus oder divergiert: Merge-Vorbereitungs-Branch + Synchronize-Schleife (gh-pr-automation §Merge-Kette). **Auf test→main läuft die VOLLE Suite** — auch Checks, die kleine PRs nie sehen: flutter-Parität (Mobile-Icons müssen Web-Kalender-Icon-Namen abdecken), datenbank (Migrations-Replay gegen schema.ts je App), test (alle betroffenen Apps). Siehe unten „Paritäts-Fallen". Der Release-Tag kommt erst, wenn alle Punkte für „ohne Handgriff beim Kunden“ (siehe unten) auch in main sind.
6. **Taggen:** lokal `main` checkout + pull. Baum muss sauber sein — lokale Only-Artefakte (z. B. `.pi/`) per `echo ".pi/" >> .git/info/exclude` ausblenden statt löschen. Trockenlauf `npm run release -- <app> X.Y.Z`, dann `npm run release -- <app> X.Y.Z --push` → Tag `<app>/vX.Y.Z` entsteht und pusht.
7. **Bau verifizieren:** build.yml-Lauf auf dem Tag per bg-Watcher bis completed; dann `gh release view <app>/vX.Y.Z` — existiert das Release und trägt es den Changelog-Abschnitt als Body? (Schritt „Release anlegen" braucht die Repo-Variable AUSLIEFERUNG_VON_GITHUB=ja; prüfbar per `gh api repos/…/variables`.) Images/OCI-Artefakte gehen nach ghcr.io — Release-Assets leer ist normal. Schon nach jedem test→main-Merge den main-Build bis zum Ende abwarten, vor allem Job `build-and-push`, Schritt „Build & push per-customer artifacts“. Er baut je Kunde ein eigenes App-Abbild und läuft NUR auf main und Tags, nie in der PR-CI. Ist er rot, kein Release-Tag, bis ein main-Build für alle Kunden grün ist; denn der Tag liefe in denselben Fehler. Rotes Log gezielt holen (`curl -sL -H "Authorization: Bearer $GH_TOKEN" …/actions/jobs/<id>/logs -o datei` + `grep`). Bricht dort `next build` mit „JavaScript heap out of memory“ ab, den Speicher unter Runner-Bedingungen messen, statt die Grenze zu raten: `references/build-speicher.md`.
8. **Abschluss-Hinweise an User:** Auslieferungshelfer braucht `FORGEJO_API=https://api.github.com/repos/MaG-TechOrg/mag-tech-monorepo` (+ Token mit Repo-Read) in seiner Deploy-Umgebung, damit die Fassung im Ankündigungsformular auftaucht; MAG-<n>-Issue vorher auf der KI-Plattform anlegen (siehe „MAG-Nummern“).
9. **aishop (KI-Gateway) abweichend:** Changelog `apps/aishop/CHANGELOG.md`, Abschnitt `## X.Y.Z — JJJJ-MM-TT` OHNE `v` und ohne Klammern, Unterabschnitte `### Neu` / `### Geändert` (keine Emojis); vor dem Commit mit `bash scripts/release/changelog-abschnitt.sh aishop X.Y.Z` prüfen, dass der Abschnitt gelesen wird. Ablauf sonst wie oben (PR → test → test→main → `npm run release -- aishop X.Y.Z [--push]` auf main). Der Tag startet nur `.github/workflows/build-aishop.yml` (Image + Deploy-Artefakt `aishop/deploy:X.Y.Z` in Harbor, `cargo test` im Bau; bricht ab, wenn die Fassung in Harbor schon existiert) und liefert NICHTS aus. Ausgeliefert wird per Knopf im Auslieferungshelfer (https://auslieferung.mag-tech.eu → Eintrag `mag-tech`, Anwendung `aishop` → Fassung freigeben; Flux folgt dem Kanal `kunde-mag-tech` binnen ~2 min). Dieser Schritt braucht die Browser-Anmeldung des Nutzers, das Dienstkonto `auslieferung-cli` darf nur Kunden anlegen; den Kanal-Tag nie direkt in Harbor setzen, weil der Helfer sonst einen anderen Soll-Stand führt. Danach `curl -s https://aishop.mag-tech.eu/api/version` = neue Fassung.

## Auslieferungsfähigkeit neuer Funktionen

- Was released wird, muss nach der Auslieferung über den Auslieferungshelfer ohne Handarbeit beim Kunden laufen, auch bei Bestandskunden: keine ENV-Änderungen auf Kunden-VPS, Freischaltung je Kunde über Lizenzmodul oder Firmen-Einstellung, und kein einziger Handgriff auf dem Server — auch kein einmaliger. Ordner, Eigentümer und Rechte (z. B. hostPath-Verzeichnisse) legt die Auslieferung selbst an: Kubernetes per initContainer, docker-compose per Init-Dienst mit `depends_on: condition: service_completed_successfully` in allen `docker-compose*.yml`-Varianten. Kommentare wie „vorher einmal `sudo install -d …`“ sind ein Befund, kein Hinweis.
- Neue Konfigurationsparameter (Konfig-Bereiche der App) in die Verhaltens-Suite `__tests__/migrations/mag-1300-konfiguration-gegen-postgres.test.ts` beider Apps aufnehmen (erwartete Schlüsselliste); sonst ist der datenbank-Check rot.
- Die Flux-Kustomization je Kunde (`apps/besichtigungs-app/k8s/customer-vm/flux/oci-repository.yaml`) legt das Artefakt mit `targetNamespace` in den Kunden-Namespace. Server-weite Komponenten erreichen Bestandskunden nur über `install-customer-cluster.sh` (Modus own-vm). Neue Dienste deshalb als Deployment in `k8s/base` ausliefern.
- Jede neue Deployment mit Harbor-Image in die `harbor-pull`-Regex derselben Datei und in `assert_images` aufnehmen. Grund: Sonst bleibt sie in ImagePullBackOff, und die Kustomization steht wegen `wait: true` auf READY=False.
- Test-Cluster `clusterapp`: Das Overlay `k8s/overlays/clusterapp/kustomization.yaml` setzt ALLE Images über EINEN Flux-Setter (`flux-system:besichtigungsapp:tag`). Ein neues Image braucht daher (a) bei jedem Bau in `build.yml` denselben Tag wie die App (bauen oder nachtaggen), sonst ImagePullBackOff, (b) einen Eintrag in `images:` mit dem Setter-Marker, (c) `ghcr-pull` als Pull-Secret und (d) kein Scheduling auf den knappen `k3s-controller`-Knoten (Taints/Allokierbares nur lesend prüfen) und (e) an JEDEM Container und initContainer `requests` UND `limits` für cpu UND memory. Grund zu (e): Der Namespace hat ein ResourceQuota, das nicht im Repo steht. Fehlt ein Wert, entsteht gar kein Pod: Die Deployment steht still auf 0/1, und nur die ReplicaSet-Ereignisse zeigen `FailedCreate … failed quota … must specify limits.cpu` (`kubectl -n <ns> get events | grep <name>`, Platz per `kubectl describe resourcequota`). Lizenzbindung neuer Funktionen vorab gegen die Testfirmen prüfen (nur lesend: `SELECT modules FROM licenses WHERE deleted_at IS NULL`). Grund: Fehlt dort das verlangte Modul, sieht der Nutzer die Funktion beim Test nicht. Dann die Bindung bis zu seiner Entscheidung lösen, nicht ENV setzen. Nach dem Merge eine Live-Probe (Pod läuft, Health, echter Funktionsaufruf über die App); eine Rollout-Wache, die auf Pod-Bereitschaft wartet, liest bei 0 Pods sofort die Ereignisse, statt bis zum Zeitlimit zu warten. Bevor ein Issue auf „bereit zum Testen“ geht, belegen, dass genau dieser Merge läuft: den Commit aus `/api/version` bzw. dem Image-Tag des Pods (`test-<lauf>-<sha>`) per `git merge-base --is-ancestor <merge-commit> <sha>` prüfen und neue Bezeichner im Server-Bundle suchen (`kubectl exec -c app <pod> -- sh -c "grep -rl <bezeichner> /app/apps/<app>/.next/server | wc -l"`, Treffer > 0). `-c app` immer angeben. Grund: Der Pod hat initContainer; ohne `-c` schreibt jeder Aufruf „Defaulted container …“ auf stderr, und ein `| tail` schneidet dann die eigentlichen Ergebnisse ab.

- Neuer Job oder neue Push-Zeile in `.github/workflows/build.yml`: Der Wächter `scripts/github-bau-pruefen.py` (Test `.github/ci/__tests__/github-bau-pruefen-test.sh`, CI-Check `waechter`) führt eine Erlaubnisliste (`ERLAUBT["build"].jobs` und erlaubte `docker push`-Zeilen). Neue Jobs dort eintragen; Images für Kunden-Harbor NICHT mit einem eigenen `docker push "$DST"` im neuen Job spiegeln, sondern im bestehenden Spiegelschritt der App (dort wartet eine `until docker pull`-Schleife auf das ghcr-Image, dann tag+push). Lokal vorab prüfen: der Test-Aufruf steht im CI-Schritt „Test k8s shell libs“; `mt-vorpush` fängt es nicht.

## Paritäts-Fallen auf test→main (kleine PRs testen sie nicht)

- **App-Kopien (zentrio-app)**: alte Snapshots der Haupt-App; sie brechen, wenn geteilte Domänen-Pakete (packages/domain-*) evolvieren, während die Kopie nicht mitgezogen wurde. Prozedur: references/anpassung-app-kopien.md.
- **Migrations-Vollständigkeit**: Der datenbank-Check replayt je App die eingecheckten .sql (numerisch nach init.sql) gegen eine Wegwerf-Postgres und verlangt Abdeckung ⊇ schema.ts. App-Kopien mit eigener Migrationskette müssen fehlende .sql der Haupt-App als Kopie mit hochlaufender Nummer nachziehen (eigene Nummern der Kopie unangetastet lassen). Lokal nachbauen: `docker run --rm postgres:16-alpine -p 5544:5432` + `DATABASE_URL=… npx tsx scripts/migrationen-vollstaendig.ts`.
- **Verhaltens-Suiten gegen Postgres (auch im Feature-PR, sobald Migrationen berührt sind)**: Der datenbank-Check führt alle `__tests__/migrations/*-gegen-postgres.test.ts` aus, darunter den Wächter „jede Tabelle hat einen record_history-Trigger oder steht mit Begründung in AUSNAHMEN“. Neue Tabelle → Trigger in der Migration oder AUSNAHMEN-Eintrag (abgeleitete Daten, Telemetrie, häufig wechselnde Lesestände). Der Vorpush führt die Suiten nicht aus; lokal in `apps/besichtigungs-app`: `MAG1148_TEST_DB=ja DATABASE_URL=<db> npx jest --runInBand __tests__/migrations/<suite>` (jede Suite hat genau einen Schalter `MAG<n>_TEST_DB`).
- **Mobile-Abdeckung neuer Server-Actions (auch schon im Feature-PR/Vorpush)**: Jede neue exportierte Action unter `apps/besichtigungs-app/src/app/actions/` braucht eine Zeile in `apps/umzugsoffice-mobile/docs/actions-abdeckung.md` (alphabetisch, Phase 0–5, „nur Web“ mit Begründung), sonst wird der Test `__tests__/mobile-abdeckung-actions-routen.test.ts` rot; neue Route-Handler analog in der Routen-Matrix. Schon beim Schreiben der Actions miteintragen, vorab prüfbar mit `jest __tests__/mobile-abdeckung`.
- **Flutter-Icon-Parität**: Web-Kalender-Icon-Namen (CALENDAR_ICON_NAMES in domain-appointments) müssen in der Mobile-Map (kalender_farben.dart) abgedeckt sein; der Paritäts-Test liest Namen per Regex — ziffernhaltige Namen (Trash2, Building2) verlangt [A-Za-z0-9]+.
- **Seitenleisten-Texte**: Jedes `label` UND jedes `titel` in `src/lib/seitenleiste.ts` muss im Wörterbuch `Menue` aller Sprachen stehen (`messages/{de,en,ru}.json`), sonst ist `__tests__/i18n/sprachen-gleich.test.ts` rot. Nach jeder Änderung an Seitenleiste oder Menünamen `npx jest __tests__/i18n __tests__/lib/primary-nav.test.ts __tests__/lib/seitenleiste.test.ts` laufen lassen, auch bei kleinen eigenen Korrekturen.
- **Wächter-Checkliste in jeden Worker-Auftrag**: neue Tabelle → mag-1148 (Trigger oder Ausnahme); neuer Konfig-Parameter → mag-1300 in BEIDEN Apps; neue Action → Mobile-Abdeckung; neuer Menütext → `Menue` de/en/ru. Grund: Diese Suiten laufen erst in der CI (datenbank, test), nicht im Vorpush; Worker übersehen sie sonst wiederholt, und jede vergessene Suite kostet eine CI-Runde von 20–25 min.

## MAG-Nummern

PR-Titel brauchen `MAG-<n>:` (CI-Job titel prüft; kein Conventional-Commits-Typ). Die Nummer kommt aus dem KI-Plattform-Issue: vor dem ersten Commit per MCP `issue_create` anlegen (POST https://agents.gamzatlab.net/api/mcp, Bearer `~/.tmp/kip_token.txt`, Header `Accept: application/json, text/event-stream`; der Server antwortet mal als reines JSON, mal als SSE-`data:`-Zeilen → immer mit `sed 's/^data: //' | jq -r '.result.content[0].text // .error.message'` lesen, nie nur `grep '^data:'`, sonst bleibt eine erfolgreiche Antwort unsichtbar und der Aufruf wird doppelt abgeschickt) und die Nummer aus der Antwort nehmen, nie raten. `issue_comment` erwartet `number` als Zahl und `bodyMd`; vor einem Wiederholungsversuch per `issue_get` prüfen, ob der Kommentar schon da ist. Fehlt das Token auf der Maschine, den Nutzer nach der Nummer fragen.
