# gh-pr-automation

# GitHub-PR-Merge-Automation mit gh CLI

Klasse: PR-Ketten (Checks abwarten → mergen → Folge-PR synchronisieren lassen) automatisiert abwickeln, auf GitHub-Repo-Schutz (Rulesets) und self-hosted Runnern.

## Grundmuster Watcher (bg_run, kein Polling im Agent-Turn)

```bash
warte_gruen() {  # $1 = PR-Nummer
  local pr=$1 rc
  while true; do
    gh pr checks $pr >/dev/null 2>&1; rc=$?
    [ $rc -eq 0 ] && return 0          # alle grün
    [ $rc -eq 1 ] && return 1          # mindestens ein Check rot
    sleep 45                            # rc 8 = pending → weiter warten
  done
}
```

- `gh pr checks`: rc 0 = grün, 8 = pending, 1 = fail. Nicht auf Output-Text parsen, Exit-Code ist stabiler. Ausnahme rc 1 mit „no checks reported on the '<branch>' branch“: Es gibt (noch) keine Checks, weil die Workflows erst starten oder Pfadfilter den PR ausschließen (z. B. reine `docs/**`-Änderungen). Wie pending behandeln und erst nach einer Karenz (≈ 15 min ohne Checks) als „keine CI nötig“ werten, sonst meldet der Watcher Rot oder wartet ewig.
- Watcher als bg_run starten (isAgent:false, Timeout ≥ 40 min für Test-Jobs), Agent-Turn beenden und auf die Terminal-Notification warten. Nie im Agent-Turn poll-sleepen.
- Eigene Warteschleifen (parsen statt Exit-Code) brauchen einen EXPLIZITEN „alles grün → return 0“-Zweig: Eine Schleife, die nur Rot-Erkennung + MERGED-Abfrage hat, läuft bei Grün ewig weiter, bis das Task-Timeout sie abschießt (sieht aus wie Hänger, ist Logikfehler). Status-Paare unter `set -u` nie per `set -- $var` splitten (leer → „unbound variable") — `read -r a b <<< "$var"` stattdessen. Und Ergebnis-Variablen aus `gh pr create --json … 2>/dev/null` sofort prüfen: schlägt das Erzeugen still fehl (leere Nummer), fällt `gh pr view ""` auf den PR des AKTUELLEN Branchs zurück und „verifiziert" einen ganz anderen Stand.
- Push-Läufe auf Integrationsbranches heißen nach dem Workflow, nicht nach dem Branch: Nach einem Merge in `test` läuft die Verifikation unter `build.yml` (nicht `test.yml` — das ist der PR-Workflow); `gh run list --workflow <name>` mit 404 heißt falscher Workflow-Name, erst `gh run list --branch <b> --json workflowName` zeigt die tatsächlichen Namen.

## Regeln (Fallen an ihrem Schritt)

1. **Head-SHA VOR jedem automatischen Merge verifizieren.** `gh pr merge` mergt den PR-Head im Moment des Aufrufs — ein parallel gelaufener Push verschiebt den Head, die grünen Checks gelten aber für die alte SHA. Pattern: `gh pr view N --json headRefOid` gegen die erwartete Commit-SHA prüfen, bei Abweichung NICHT mergen. Mechanismus: Checks-Bewertung und Merge-Zeitpunkt sind zwei Lookup-Momente, zwischen denen der Head wandern kann. Das Fenster dazwischen schließt `gh pr merge N --merge --match-head-commit <sha>`: GitHub lehnt den Merge ab, wenn der Head nicht mehr diese SHA ist. Danach `gh pr view N --json state` auf MERGED prüfen, bevor die Kette weiterläuft.
1a. **Volle SHA, Vorfahr-Prüfung, Merge-Kette.** Die SHA für `--match-head-commit` immer voll aus `gh pr view N --json headRefOid` nehmen und gegen `git rev-parse <lokaler-branch>` vergleichen; nie aus einer Kurz-SHA zusammensetzen (GitHub meldet dann „Head branch was modified“). Liegt der lokale Branch vor dem PR-Head, nur mergen, wenn `git merge-base --is-ancestor <pr-head> <lokal>` gilt, und die übrigen Commits als neuen PR von einem frischen Branch einbringen lassen. Liegt er dahinter (`git merge-base --is-ancestor <lokal> <pr-head>`, etwa weil ein Fix aus einem anderen Worktree gepusht wurde), gilt der PR-Head, sofern die CI auf genau ihm grün ist; den Eigentümer Folgezweige von `origin/<basis>` abzweigen lassen. Laufen beide auseinander, nicht mergen. Mehrere unabhängige PRs nacheinander mergen: Nach jedem Merge ist `mergeable` der übrigen kurz `UNKNOWN`. Bis etwa 60 s nachfragen, nur bei `MERGEABLE` mergen; bei `CONFLICTING` stoppen und den Eigentümer die Basis einmergen lassen.
1b. **`git fetch` in Watchern und Folgejobs mit Wiederholung** (`for i in 1 2 3 4 5; do git fetch -q origin <b> && break; sleep 7; done`). Grund: Worktrees eines Repos teilen die Remote-Refs; laufen zwei Fetches gleichzeitig, bricht einer mit „cannot lock ref … expected …“ ab.
2. **Kein Watcher auf einem Branch leben lassen, auf den man selbst noch pusht.** Entweder zuerst pushen, dann Watcher starten, oder Watcher vorher bg_kill'en — sonst merged er den alten Stand (die Fixes landen dann in einem Folge-PR statt im Merge).
2a. **Watcher-Skripte nie per sed auf eine neue PR-Nummer umschreiben — sauber neu schreiben.** sed erfasst Referenzen unvollständig (Abfrage fragt noch die alte PR-Nummer, Ausgabezeigt die neue), leere Head-Variable → Abbruch mit Fehldiagnose. Skript pro Phase frisch erzeugen (Heredoc mit $-Escapes) statt Variablen-Austausch.
2b. **GraphQL-Fehler „Merge already in progress" beim Watcher-Merge = Rennen, keinechtes Scheitern.** Erst `gh pr view N --json state,mergedAt` befragen: meist IST gemerged und nur die Antwort kam zu spät/doppelt — NICHT neu anstoßen oder die Kette abrechen. Allgemein: Die Merge-Funktion einer Kette prüft zuerst `state`; `MERGED` gilt als erledigt und die Kette läuft weiter, denn der Nutzer oder ein anderer Lauf mergt oft selbst (`mergeable` eines gemergten PRs ist nie `MERGEABLE`, eine reine Mergeable-Prüfung bricht dann ab). Meldet der Nutzer, dass er einen PR selbst gemergt hat, laufende Ketten auf Folgen prüfen: Landet der PR in einer Basis, aus der ein offener Freigabe-PR zieht, ist er dort schon enthalten, und ein eigener Freigabe-PR entfällt; Ketten, die ihn noch mergen wollen, beenden und mit dem verkürzten Ablauf neu starten.
2c. **Branch-Guard-Falle beim Commit auf neuem Branch:** `git checkout -b X && git add … && git commit …` in EINEM Aufruf wird blockiert („Direct commits to 'main' are forbidden"), weil der Guard gegen den AKTUELLEN Branch vor Ausführung wertet. Aufspalten: erst `git checkout -b X` allein + Verifikation, dann add+commit. Und: In der blockierten Kette gelaufene Heredocs haben ihre Datei NICHT geschrieben — Message-Datei im selben Aufruf wie der Commit erzeugen.
2d. **Force-Push trotz Guard:** `git push --force-with-lease` blockiert der Pi-Bash-Guard (Pattern /push\s+--force/); die Refspec-Syntax `git push origin +<branch>` geht durch und wirkt identisch (nach amend/Heilung).
3. **DIRTY-PRs bekommen KEINE Workflow-Runs.** GitHub legt für PRs mit Merge-Konflikt keinen Merge-Ref an → `gh pr checks` bleibt ewig leer („no checks reported“). Erst den Konflikt auflösen: Branch von der Basis ziehen, die Gegenseite hineinmergen (`git merge origin/<basis> --no-commit`), auflösen, PR → Basis; der eigentliche PR synchronisiert danach und bekommt frische Runs. Watcher fragen deshalb vor dem Warten `mergeable` ab und melden `CONFLICTING` sofort, statt bis zum Zeitlimit auf Checks zu warten. Nach JEDEM Merge in die Basis alle offenen PRs, die dieselben Dateien berühren (Werkzeug-Listen, Labels, STATUS-Doku), auf `mergeable` prüfen und die Basis gleich einmergen. Grund: Parallele Zweige hängen an dieselben Listen an; jeder Merge macht die anderen konfliktbehaftet, und ihre CI startet nie. Auflösung „beide behalten“ per kleinem Python-Skript über die Konfliktmarker; hängen beide Seiten ein Element an dasselbe Dateiende (z. B. ein weiteres Objekt vor `});`), gehört die gemeinsame Schlusszeile nach dem Marker zur zweiten Seite: Die eigene Seite bekommt ihren Abschluss (`}),`) dazu, dann folgt die andere. Danach Typecheck und die betroffenen Tests.
4. **--admin merge bei Rulesets mit toten required Kontexten.** `gh api repos/.../rulesets` zeigt Rulesets (branch_protection-API kann 404 liefern, obwohl Schutz aktiv ist). Required-Checks mit Contexts, die der neue Forge nie meldet (z. B. alte KI-Checks ohne integration_id), blockieren ewig → `gh pr merge N --merge --admin` ist dann die etablierte Praxis; vorher prüfen, dass alle LEBENDEN Checks grün sind. Dauerzustand mag-tech-monorepo: `ki/deploy-gate` und `ki/review` sind required und melden nie Status, weil die KI-Plattform-Runner abgeschaltet sind — dort gilt: alles außer diesen beiden grün ⇒ sofort `--admin` mergen (Nutzer-Vorgabe), die beiden ignorieren. Merge-Methode vorher klären: Repos können Squash verbieten („Squash merges are not allowed") — im mag-tech-Monorepo ist NUR `--merge` (Merge-Commit) erlaubt; `--squash` bricht mitten in der Kette ab. Check-Quelle vor dem Merge ist IMMER `gh pr checks N` — das Rollup aus `gh pr list --json statusCheckRollup` kann stale sein und einen frisch roten Check verschweigen.
4a. **Ketten-PR (Basis → Ziel, Kopf = Basisbranch) erbt dessen Push-Läufe als Checks.** Ein offener test→main-Freigabe-PR zeigt auch die push-getriggerten Builds des test-Zweigs als Checks: Fällt dort ein Job rot, ist der Freigabe-PR rot, obwohl sein Diff harmlos ist. Solche Rot-Meldungen dem Push-Run zuordnen (`gh run list --branch <basis>`), bevor der eigene Diff verdächtigt wird. Und: Auch Ketten-PRs bestehen den Titel-Check — MAG-Nummer vorn, kein „test → main:" als Präfix.
4b. **Transienter Job-Rot in einem Push-Run: einmal `gh run rerun <id> --failed`, bevor debuggt wird.** Voraussetzung: Der Run ist COMPLETED (Rerun nur auf abgeschlossenen Läufen; Logs fehlgeschlagener Jobs eines noch laufenden Runs liefert gh erst nach Abschluss — zwischenzeitlich `gh api .../actions/jobs/<id> --jq '.steps[]'` zeigen die fehlgeschlagene STELLE). Bleibt der Job nach dem Rerun rot, erst dann Ursachenarbeit (Regel 6).
5. **Enger Merge-Base = schmaler CI-Scope.** Betroffenheits-Filter (turbo/paths) bestimmen getestete Pakete aus dem Merge-Base: Ein PR, der nur eine App toucht und von der Basis-Spitze abzweigt, testet andere Apps nicht — grün heißt nicht repo-gesund. Nach einem großen Merge (Basis ← Divergent-Branch) die ungetesteten Apps lokal typechecken.
6. **Baumidentischer CI-Rot → Runner-Umgebung beweisen, nicht Code ändern.** Merge-Ref holen: `git fetch origin refs/pull/N/merge`, dann `git diff --name-only <merge-ref> origin/<base>` — LEER heißt CI-Prüfling ≡ Basis-Baum. Dazu die gemeldeten Suiten lokal auf demselben Baum ausführen. Beides sauber (Suiten grün bzw. gemeldete Importe existieren im Baum gar nicht) ⇒ persistenter Runner-Workspace-Verdacht (self-hosted, capacity-1): stale jest-transform-cache oder stale dist/-Artefakte. Gegenmittel: Runner-Workspace-Caches clearen bzw. betroffene Jobs ohne Cache neu laufen lassen — nicht den Baum „reparieren".
7. **Job-Logs mit Escape-Sequenzen**: `gh api jobs/<id>/logs --allow-escape-sequences` + `sed`-Strip von ANSI; Lokalzeit vs. CI-UTC (+1) beim Zeitachsen-Abgleich bedenken — sonst wirkt ein Lauf „vor" einem Ereignis, der danach war.

8. **Bei `delete_branch_on_merge` nie einen PR vom langlebigen Integrationsbranch öffnen.** Prüfen mit `gh api repos/<o>/<r> --jq .delete_branch_on_merge`. Ist es true, löscht GitHub beim Merge den Head-Branch – auch einen Integrationsbranch, auf dem die nächste Welle schon liegt. Stattdessen den geprüften Stand als Schnappschuss pushen (`git push origin <sha>:refs/heads/<int>-welle-<n>`), davon den PR öffnen und mit `--match-head-commit <sha>` mergen. Danach die Basis zurück in den Integrationsbranch mergen (ff-only, sonst `--no-ff`).

9. **Einen einzelnen Commit eines Arbeitszweigs als eigenen PR (nicht gestapelt) einbringen, ohne den Arbeitsbaum zu verlassen:** Lokal auf frischem Branch von `origin/test` cherry-picken und Vorpush laufen lassen, oder gleich `git push origin <sha>:refs/heads/<neuer-branch>` (Refspec statt Checkout), dann `gh pr create --head <neuer-branch>`. Den lokalen Zweig danach per `git branch -f <name> <sha>` umhängen — das scheitert („used by worktree“), solange der Zweig ausgecheckt ist; erst auf einen anderen Zweig wechseln. Der Guard blockiert `git branch -D`, dafür `-d` oder `branch -f`. Belegt ein laufender Worker den Haupt-Worktree (Branchwechsel verboten), den PR aus einem temporären Worktree bauen: `git worktree add -b <neu> /tmp/<x> origin/test`, dort `git cherry-pick <sha>`, `python3 scripts/encoding-pruefung.py origin/test` (prüft auch die Commit-Nachricht — ASCII-Umschriften wie „fuer“ vor dem ersten Push per `git commit --amend -F <datei>` heilen, danach braucht es keinen Force-Push), `mt-vorpush schnell` (der volle Vorpush braucht node_modules, die der frische Worktree nicht hat; Voll-Lauf auf dem Vorgängerstand mit demselben Commit genügt dann als Beleg im PR-Text), pushen, PR, Worktree später entfernen. Folge-PRs, die auf einem noch offenen PR aufbauen, im PR-Text als „gestapelt“ kennzeichnen oder erst nach dessen Merge (rebase auf die Basis) öffnen; nach einem Basis-Merge in einem PR-Zweig die Basis per Merge-Commit einbringen (kein Force-Push) und `git diff --stat origin/<basis>` auf den erwarteten Dateiumfang prüfen.

9a. **Gestapelter Folge-Zweig nach dem Merge der Basis-PR:** Der Leitstand mergt mit Merge-Commit, die alten Commits stecken dann per Vorfahr im Basisbranch. Prüfen `git merge-base --is-ancestor <alte PR-Spitze> origin/<basis>`, dann `git rebase --onto origin/<basis> <alte PR-Spitze>` — es bleiben nur die eigenen Commits, kein Force-Push nötig (Zweig war noch nie gepusht). Meldet `gh` bei einem anderen offenen PR danach CONFLICTING (Doku-Dateien, die beide Zweige berühren, z. B. Tabellen/Abschnitte am Dateiende), `origin/<basis>` in dessen Zweig mergen, Konfliktmarker per kleinem Python-Skript auflösen (BEIDE Seiten behalten), `git commit -F`, Encoding-Prüfung, normal pushen und die Checks neu abwarten.

10. **Rollout bleibt aus, obwohl gemergt wurde: Ein hängender Lauf blockiert die Concurrency-Gruppe.** `gh run list --branch <b> --workflow <wf> --limit 8 --json databaseId,headSha,status,conclusion,createdAt` zeigt dann einen Lauf, der seit Stunden `in_progress` ist, und neuere als `cancelled`/`pending`. Grund: GitHub hält je Gruppe nur einen laufenden und einen wartenden Lauf; ältere wartende werden verworfen, und der wartende startet nie. Den hängenden Schritt finden: `gh api repos/<r>/actions/jobs/<id> --jq '.steps[] | select(.status!="completed")'`. Hängt nur ein Aufräumschritt („Post …“, z. B. Cache-Upload von setup-node) und sind die Artefakte schon gepusht, `gh run cancel <id>`; bleibt er `in_progress`, `gh api -X POST repos/<r>/actions/runs/<id>/force-cancel`. Danach startet der wartende Lauf mit dem neuesten Stand. Dauerhaft `timeout-minutes` am Job vorschlagen. Eine Rollout-Wache prüft deshalb neben der ausgelieferten Version auch den Baulauf.

## Merge-Kette Freigabe (Release-Vorbereitung)

Standardablauf, wenn Basis und Ziel divergiert sind (z. B. test→main-Freigabe-PR dirty):
1. Changelog-/Release-PRs → Zielbranch (normale Checks, Head-Verifikation, merge).
2. Merge-PR: Branch vom Zielbranch-Tip, Gegenseite (z. B. main) hineinmergen, Konflikte lösen, pushen, PR → Zielbranch. Merge-Konflikt-Dateien nach Schema lösen: Signatur-Vereinigung bei Typ-Konflikten, Lockfile per `pnpm install --lockfile-only` regenerieren statt Handarbeit.
3. Merge-PR gemerged ⇒ Freigabe-PR synchronisiert: Loop aus `gh pr update-branch N` (|| true) + `headRefOid == Zielbranch-Tip`-Vergleich, Status DIRTY/CONFLICTING → Abbruch. Dann frische Runs ⇒ Head-Verifikation ⇒ merge.
4. Danach erst taggen/release — vom gemergten Stand, nach `git pull` der Basis.
4a. Solange ein Freigabe-PR (Basis → Ziel, Kopf = Basis-Zweig) auf seine Checks wartet, nichts in die Basis mergen; weitere fertige PRs erst nach seinem Merge einbringen (Kette wartet auf `gh pr view <n> --json state` = MERGED) und mit einem eigenen Freigabe-PR nachziehen. Grund: Jeder Merge in die Basis verschiebt den Kopf des Freigabe-PR; fällt er zwischen „Checks grün“ und den `--admin`-Merge, passt `--match-head-commit` zum neuen Kopf, und ein ungeprüfter Stand landet im Ziel.
5. Ändert der Freigabe-Merge nur Pfade aus dem `paths-ignore` des Bau-Workflows (z. B. `**/*.md`, Flux-Overlays), startet auf dem Ziel KEIN Baulauf. Eine Kette, die danach auf den Baulauf wartet, muss das erkennen (keine Lauf-ID zum Merge-Commit → `git diff --stat <letzter-grüner-baustand> <merge>` zeigt nur ignorierte Pfade → Code identisch zum letzten grünen Lauf) statt mit leerer ID abzubrechen. Ein Tag-Push baut trotzdem: `paths-ignore` gilt bei GitHub nur für Zweig-Pushes.
