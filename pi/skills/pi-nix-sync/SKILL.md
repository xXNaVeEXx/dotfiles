# Pi-Verteilung über nix-conf + dotfiles

Architektur: nix-conf installiert Pi (Flake-Input `github:earendil-works/pi/<rev>`, Rev manuell gebumpt) via `myHome.pi.enable` auf allen Gamzat-Maschinen; `pi-sync` spiegelt den konfigurierbaren Slice von `~/.pi/agent` über den dotfiles-Klon `~/projects/dotfiles` (Subtree `pi/`) per Git.

## Beteiligte Stellen
- `~/projects/nix-conf/flake.nix`: Input `pi` (per fester Rev gepinnt, KEIN nixpkgs-follow — pi bringt sein getestetes Lock mit; Bump-Hinweis steht als Kommentar an der URL), wird via `extraSpecialArgs`/`specialArgs` an home-module durchgereicht (3 Stellen: mkHomeLinux, nixos, darwin).
- `~/projects/nix-conf/home/modules/pi.nix`: Paket + `pi-sync`-Skript + systemd-User-Timer (nur Linux, darwin nur Skript+Activation) + Bootstrap (Erst-Pull wenn `~/.pi/agent/skills` leer).
- `~/projects/nix-conf/home/options.nix`: `myHome.pi.enable` (mkEnableOption-Muster des Repos).
- Enables: `home/gamzat-cachyos.nix`, `gamzat-shared.nix`, `gamzat.nix` (nixos), `gamzat-omarchy.nix` (aarch64), `gamzat-darwin.nix`. maga/marv kriegen Pi NICHT.
- dotfiles-Repo `github:xXNaVeEXx/dotfiles`: Subtree `pi/` = AGENTS.md, settings.json, keybindings.json, skills/, extensions/ (OHNE node_modules — Symlink-Farm, regenerierbar), hermes-mind/{MEMORY.md,USER.md,config.json}.

## Sync-Umfang (was bewusst NICHT reingeht)
- auth.json: Provider-Tokens, bewusst pro Maschine → 1× `/login` je Machine (sops-Ausbau wäre später möglich, age-Key fehlt bisher auf Maschinen).
- Lokal/riesig/regenerierbar: npm/ (1012M, aus settings.json via `pi install`), install/, sessions/, backups/, ext-dev/, missions/, usage-history/, web-search-cache/, models-store.json, *.log, sessions.db*.

## Prozedur: Änderungen an der Verteilung
1. dotfiles: /tmp-Klon aktualisieren (`git pull`), pi/-Subtree ändern, Branch + Conventional-Commit, landen via `GIT_BIGPOWERS_LAND=1 bash <bigpowers>/scripts/land-branch.sh <branch> "<type>(scope): <subject>"` (guard-git/omp-hooks blocken Agent-Commits UND -Pushes direkt auf main — auch `git commit` alleine).
2. nix-conf: Modul/Option/Enables ändern, NEUE DATEIEN ZUERST `git add`en (Flake-Evaluation sieht nur getrackte Dateien — sonst „Path … is not tracked by Git"), dann Branch + land-branch.
   - land-branch-Requirements: Branch VOR dem Commit mit `git checkout -b <name>` anlegen (ein Commit direkt auf main lässt land-branch mit „Feature branch does not exist" abbrechen), Branch muss auf aktuellem origin/main basieren (sonst „not based on current main" → rebase), Commit-Subject ≤ 72 Zeichen (guard-git blockt sonst den Commit), Working Tree auf main muss clean sein → nicht-branch-Dateien vorher `git stash push -m … <dateien>`, nach dem Land `git stash pop`.
   - `git add` allein genügt nicht: land-branch wechselt bei einem nur gestellten (uncommitted) Edit zurück auf main, findet den Tree dort dirty und bricht ab — Commits IMMER auf dem Branch abschließen (`git commit`) und erst dann landen. Ein beim Hin- und Herwechseln liegen gebliebener Edit auf main vorher per `git stash push -m … <datei>` sichern, auf den Branch wechseln und dort `git stash pop`. Einen versehentlich leeren Branch NICHT mit `git branch -D` entfernen (guard-git blockt das) — `git checkout main` reicht, der Branch bleibt als leeres Ref und ist harmlos.
3. Pi-Version heben: Ziel-Rev per `git ls-remote --tags https://github.com/earendil-works/pi.git` holen (Tags seit dem Upstream-Fix „workspace lockfile integrity“ bauen direkt unter Nix; sonst main-Rev ab jenem Fix nehmen), Rev in der Input-URL von flake.nix ersetzen, `nix flake lock --update-input pi`, Build-Verifikation `nix build .#homeConfigurations.<user>@<host>.activationPackage --no-link`. Host-Attr vorher am Live-System feststellen (`hostname` + `uname -m`) — Sessions laufen auf beliebigen Maschinen, nicht nur dem Steuer-Host; der falsche Host scheitert erst im Build mit „platform mismatch“. Ein fehlendes neues Modell im /model-Picker ist meist dasselbe Symptom: der pi.dev-Modellkatalog verlangt dann eine neuere pi-Version (Stolperfalle „Neues Modell fehlt“).
4. Rebuild je Machine: `cd ~/projects/nix-conf && home-manager switch --flake .#gamzat@cachydeck` (shared/gamzat-dev: `.#gamzat@shared` bzw. `.#gamzat@gamzat-dev`; omarchy: `.#gamzat@omarchy`). macbookpro (nix-darwin) ist VERALTET — die MacBook-Pro-Hardware fährt seit der Asahi-Umstellung omarchy; der darwinConfigurations-Eintrag bleibt nur als dokumentierte Rückfall-Ebene (Kommentar in flake.nix) und wird nicht mehr gepflegt.
   - Kern-Update abgeschlossen ≠ laufende Session auf dem neuen Kern: eine resumed Session (`pi --resume <file>`) stellt ihr eigenes Modell aus der Session-Datei wieder her und überdeckt dabei `PI_MODEL` — das neue Modell in der laufenden Session per `/model <id>` wählen; nur frische Sessions starten mit `defaultModel`. Eigenen Neustart aus der laufenden Session via `nohup bash -c 'sleep 25; herdr pane send-keys <eigene-pane> ctrl+d; sleep 5; herdr pane send-text <eigene-pane> "pi --resume <session>.jsonl"; herdr pane send-keys <eigene-pane> Enter' &` (eigene Pane per `herdr pane list` an cwd/Session-Datei finden); den neuen Prozess per `ps -o lstart= -p $PPID` gegen die Switch-Zeit belegen, nicht annehmen.
5. Verifikation: `which pi`, `pi --version`, `pi-sync` einmal manuell, `systemctl --user list-timers pi-sync.timer` (darwin: `launchctl list | grep pi-sync`), Klon-Status `git -C ~/projects/dotfiles log --oneline -1`. Gedächtnis-Gleichstand über Maschinen per Hash beweisen, nicht annehmen: `md5sum` (Linux) bzw. `md5 -q` (macOS) über `~/.pi/agent/hermes-mind/{MEMORY.md,USER.md,config.json}` lokal und via SSH vergleichen.


2. Reload je fremder Pane: `herdr pane send-text <pane_id> "/reload"` und `herdr pane send-keys <pane_id> Enter`.
3. Verifikation: `herdr pane read <pane> --source recent --lines 300 | grep 'Reloaded keybindings'` — kleine Lesefenster zeigen falsch-negativ (Bestätigungszeile sitzt weiter oben; `--source visible` für den Live-Screen). `herdr agent prompt <pane> "/reload"` meldet `agent_prompt_stalled` (Slash-Commands erzeugen keinen working-State), wurde aber trotzdem ausgeführt; `--timeout` nur mit `--wait` gültig.
4. Eigene Session: nach Turn-Ende selbst nachladen via `nohup bash -c 'sleep 15; herdr pane send-text <eigene-pane> "/reload"; herdr pane send-keys <eigene-pane> Enter' &` — nie inline im eigenen Turn.
- acp_delegate-/bg-Worker überleben `/reload` (eigene Prozesse); ihr Widget zeigt weiterlaufende Sekunden als Beweis.
- `/reload` tauscht NUR Erweiterungen, nie den pi-Kern: Ein frisch gesynctes pi-lens auf einem uralten Kern crasht bei jedem Tool-Result (z. B. `getOpaqueBaselineStore(...).has is not a function` unter pi-1.3.0-Kern). Vor dem Fleet-Reload Prozesstartdaten prüfen (`ps -o lstart= -p <pids>` gegen das Datum des letzten pi-Upgrades) — Sessions mit Kern älter als die vorherige pi-Version nicht blind reloaden, sondern sauber neu starten: bei lebender Pane zuerst kontrolliert beenden (`herdr pane send-keys <pane> ctrl+d` bei leerem Eingabefeld; Alternativen aus keybindings: `app.exit`=ctrl+d, `app.clear`/Exit=ctrl+c doppelt), nur hartnäckige Prozesse mit kill -9 (SIGTERM ignorieren TUIs; Session-Datei bleibt in jedem Fall) und `pi --resume <session>.jsonl` in der Pane starten. Pane bereits zu? Prozess ist dann Orphan und muss explizit getötet werden.

## Stolperfallen
- `which pi` kann auf mise-Maschinen einen mise-Shim melden, der den Nix-Pi nur überdeckt: Bei inaktivem mise-Tool reicht der Shim an PATH durch, Nix ist der echte Lieferant. Versionscheck daher per `~/.nix-profile/bin/pi --version`; schlummernde mise-Pi-Installationen ignorieren.
- Falsch-negativer Reload-Nachweis durch zu kleines `herdr pane read`-Fenster: erst ab ~300 Zeilen suchen, sonst wirkt eine erfolgreiche Session als unverändert.
- Neue .nix-Datei untracked → Flake-Fehler beim switch: Datei VOR der Evaluation `git add`en. Schlimmere Variante: fehlt das homeConfigurations-Attr STILL (z. B. Klon aus einer Parallel-Historie, in der die Registrierung nie committet war, während die Home-Datei untracked im Tree liegt), meldet `switch --flake …#<user>@<host>` nur „flake does not provide attribute homeConfigurations.<name>" OHNE Eval-Fehler. Diagnose: `nix eval <flake>#homeConfigurations --apply builtins.attrNames` + `git status --short` + `git log --oneline -3` im Klon. Reparatur bevorzugt über frischen Klon vom Origin (mit land-branch gelandete Commits) statt merge/cherry-pick über „unrelated histories" — nur echte lokale Alleinstände (z. B. Modul-Fixes) als Branch auf dem alten Klon sichern und dort einzeln übernehmen.
- `mkHomeLinux` nimmt den System-Parameter je homeConfiguration (cachydeck/shared/maga/marv = x86_64-linux, omarchy = aarch64-linux) — Host-Attr niemals raten: Der Fehler fällt erst im Build als „Cannot build … Reason: platform mismatch (Required system: 'x86_64-linux', Current system: 'aarch64-linux')“ und wird bei gepipeten Befehlen sogar zum falsch-grünen Exit 0.
- bg_run/bash mit Pipe (`| tail`) verschluckt den Exit-Code des eigentlichen Befehls (Pipe liefert tail-RC zurück) → Rebuilds ungepiped starten oder `PIPESTATUS` prüfen; ein angehängtes `echo RC=$?` prüft ebenso nur das LETZTE Pipeline-Glied (tail), nicht den Build; ein `cmd | head || fallback` läuft zudem nie, weil das `||` nur heads RC 0 sieht — Fallback-Logik nur mit `PIPESTATUS` oder zwischengespeichertem RC, nie mit `||` hinter einer Pipe; einen „completed"-Exit-0 immer gegen die Log-Tail auf echte Fehler prüfen. Zusätzlich deckt `ssh <host> "cmd; echo RC=$?"` den Remote-Exit zu: der `echo` läuft lokal und meldet immer 0 — den RCREMOTE per `${pipestatus[1]}`/`$?` INNERHALB der Remote-Shell auflösen (`ssh <host> 'cmd; echo RC=$?'` in Single-Quotes) oder das Remote-Log auf die eigene RC-Zeile lesen. Ein bg_run-Output kann nach Abschluss leer sein (Prozess endete vor dem Flush) — dann am Zielsystem direkt nachprüfen (z. B. `~/.nix-profile/bin/pi --version`), nicht aus dem leeren Log auf Erfolg oder Misserfolg schließen.
- Neues Modell fehlt im /model-Picker, obwohl der Provider es anbietet (z. B. frische GLM-Version): pi zieht die Modellliste zur Laufzeit von pi.dev, und der Server liefert nur Kataloge, deren `minimumPiVersion` ≤ eigener pi-Version ist — alte pi-Clients sehen neue Modelle bewusst nicht. Gating beweisen: `curl -s -H 'User-Agent: pi/<version> (linux; node v22; x64)' 'https://pi.dev/api/models/providers/<provider-id>?types=chat,image,classifier'` und Modell-IDs über Versionen hinweg vergleichen. Den UA exakt im Format `pi/<semver> (…)` senden — ein unpassender UA wird serverseitig nicht geparst und erhält den NEUESTEN Katalog → falsch-positive Diagnose. Lokaler Cache `~/.pi/agent/models-store.json` (etag/lastModified/checkedAt, Remote-Check ~alle 4 h); Quelle der Kataloge ist models.dev, das der pi-Release einbrennt.
- Erstlauf von pi-sync klont nach `~/projects/dotfiles`; schlägt SSH fehl, exitiert er still (Timer retryt). /tmp/dotfiles ist NICHT der Sync-Klon.
- Rebuilds im Hintergrund (bg_run) in nix-conf: der Dirty-Tree-Prompt von `rebuild.sh` (`read -n 1`) exitet ohne TTY sofort mit RC 1, Log zeigt nur die Warnzeile → `printf 'y\n' | ./rebuild.sh …` voranstellen. Danach scheitert darwin `switch` an sudo ohne Passwort-TTY (tty_tickets verhindert Vorab-Caching) → im Hintergrund stattdessen sudo-frei `darwin-rebuild build --flake .#<host>` validieren und die Aktivierung dem User-interaktiven `./rebuild.sh switch` überlassen (Home-Manager-only-Ziele auf Linux brauchen kein sudo und laufen komplett im Hintergrund durch).
- pi-sync überschreibt lokale Divergenzen im Sync-Slice im Last-Pusher-Wins-Verfahren; Git-Historie im Klon bleibt Rückgrat.
- Timer-Service läuft ohne TTY/Agent: git push kann ohne SSH-Agent scheitern — toleriert, nächster Lauf retryt.
- Rückroll-Gefahr: Eine Maschine mit altem Live-Stand kann ältere Inhalte über neuere Commits pushen. Ursache war der mtime-only-Guard: Er las Pull-Echos als lokale Änderungen (Schritt 5 rsync -a setzt Live-mtimes auf Pull-Zeit). Fix: cmp-Inhaltsvergleich im Push-Teil (fe429f4); Maschinen ohne Rebuild haben noch das alte pi-sync und können weiter zurückrollen.
- NEUE-MASCHINE-Falle (Variante der Rückroll-Gefahr): Der Bootstrap-erst-Pull füllt ~/.pi/agent NUR, wenn `skills/` komplett leer ist. Ein nicht-leerer skills-Ordner aus Fremdquelle (Distro-Installer-Skills) unterdrückt das Befüllen — der Push-Teil läuft trotzdem und spiegelt den verarmten Live-Stand als Löschungen (extensions/, skills/) ins Repo. Deshalb: VOR dem ersten pi-sync auf einer neuen Maschine prüfen, dass skills leer ist; ist er fremd-gefüllt, Klon anlegen, Live manuell aus `pi/` des Klons befüllen (cp -r skills/. extensions/. + settings/keybindings/AGENTS/hermes-mind) und erst DANN pi-sync/Timer starten. Timer der neuen Maschine sofort `disable --now`, solange Klon oder Live divergent stehen.
- Recovery nach leerem Push: auf einer Maschine mit vollständigem Live-Stand pi-sync MANUELL laufen lassen (pull überschreibt vollen Live nicht, push stellt das Repo komplett her); neue Maschine danach Klon löschen und frisch klonen (divergente History vermeiden), Live erneut aus `pi/` füllen.
- `systemctl --user` aus SSH root→runuser schlägt mit „Failed to connect to user scope bus" → immer `runuser -u <user> -- env XDG_RUNTIME_DIR=/run/user/$(id -u <user>) systemctl --user …`.
- guard-git blockt gefürchtete git-Befehle auch INNERHALB von ssh-Remote-Befehlsstrings (Pattern matcht den ganzen Befehl). Remote-Klon ohne lokale Änderungen einfach löschen und neu klonen, statt `reset --hard` remote ausführen zu wollen.
  - Nach eigenen Skill-/Memory-Änderungen den nächsten Timer-Lauf (~20 min) abwarten und prüfen: `git -C ~/projects/dotfiles log --format='%h %an %ad %s' --date=format:%H:%M -8 -- pi/skills/<name>` (Commit einer anderen Maschine nach meinem?) und die neue Zeile per `grep` in der Live-Datei. Fehlt sie, über skill_manage neu einspielen.
  - Nach einem Rückroll jede eigene Änderung einzeln prüfen, nicht nur die auffälligen. Grund: Wiederherstellungs-Commits übersehen leicht einzelne Dateien.
  - Beim Manuell-Arbeiten im Klon: immer ERST Live reparieren, DANN Klon (sonst überschreibt der nächste Timer-Lauf den Klon-Stand mit dem alten Live-Stand).
- In nix writeShellScriptBin (''-Strings) ist `read -d ''` ein Syntaxbruch (`''` startet nix-Escape) → `'''` schreiben (5e3f7b6).
- Schlägt eine HM-Aktivierung nach „remove home-manager-path" fehl (z. B. File-Kollision wie manuelles `nix profile install gh` vs. gh-Modul), ist das home-manager-Binary selbst weg und `nix profile rollback` scheitert (Generation 0) → Rettung: `nix run nixpkgs#home-manager -- switch --flake .#<host>`. Darwin-Activation braucht ROOT: `sudo darwin-rebuild switch --flake .#macbookpro` (remote ohne Passwort nicht automatisierbar).
- Repo-Pfad ist maschinenabhängig (darwin: `~/nix-config`, nixos-Host: eigener Klon in `/etc/nixos` mit weekly `system.autoUpgrade`, andere: `~/projects/nix-conf`) — Pfad am Live-System verifizieren, nie blind aus diesem Skill übernehmen.
- Fleet-Rebuild über `ssh <host> "home-manager switch …"` scheitert im nicht-interaktiven SSH-PATH ZWEISTUFIG: erst ist `home-manager` nicht gefunden (RC 127, „command not found“), nach Fix über `~/.nix-profile/bin/home-manager` fehlt danach `nix` selbst („Zeile 552: nix: Kommando nicht gefunden“). Fix: `ssh <host> 'export PATH=/nix/var/nix/profiles/default/bin:$PATH; ~/.nix-profile/bin/home-manager switch --flake <absoluter-pfad>#<attr> 2>&1 | tail -N; echo HM_EXIT=${pipestatus[1]}'` — Flake-Ref als `/absoluter-pfad#attr` OHNE Punkt vor der Raute (`dir.#attr` wertet nix als Verzeichnis `dir.` → „No such file or directory“); pipestatus deckt zugleich die Pipe-Maskierung ab; den gemeldeten bg_run-Exit-0 nie als Build-Erfolg werten, immer den Echo-RC im Log lesen.
- nixos-Host-Update ist ROOT-only, wenn der Klon `/etc/nixos` inkl. `.git` root-owned ist: `git config --global --add safe.directory /etc/nixos` behebt NUR die Flake-Eval-Meldung („repository path is not owned by current user“) — `git pull` als User scheitert trotzdem an fehlenden Schreibrechten in `.git/refs` (root:root 755). sudo-freier Remote-Vorab-Build ist dort unmöglich; kompletten Update (`sudo -i; cd /etc/nixos && git pull && nixos-rebuild switch --flake .#nixos`) dem User überlassen oder weekly `system.autoUpgrade` (läuft als root, pullt aber nicht von selbst) machen lassen.
- Git-Push fragt nach Login und scheitert mit „authentication failed" → Repo hängt an HTTPS-Remote; GitHub nimmt Passwort-Auth nicht mehr an. Diagnose: `git remote -v` + SSH-Test `ssh -T git@github.com` (erwartet: „Hi <user>!"), Fix: `git remote set-url origin git@github.com:<user>/<repo>.git`. Bei mehreren Klonen pro Maschine jedes Repo einzeln prüfen. Ist der SSH-Key auf der Zielmaschine nicht vorhanden, GitHub-Öffnung via `https`-Klon möglich; Neuerungen zwischen Maschinen stattdessen per `git fetch ssh://<user>@<anderer-host>/pfad/zum/repo <branch>` direkt von Maschine zu Maschine holen und dort `cherry-pick FETCH_HEAD` (merge schlägt bei divergenter Klon-Historie mit „refusing to merge unrelated histories" fehl).
- Der erste Home-Manager-Switch auf einer frischen Nix-Maschine (Determinate-Installer) braucht `bash -lc` (Login-Shell lädt /etc/profile.d/nix.sh): ohne sie bricht `nix run nixpkgs#home-manager` mit „nix: command not found" ab, und ein relativer Flake-Verweis `.#attr` kann mit der nixpkgs-hm-Version als Attribut-Fehler („does not provide attribute … homeConfigurations") fehlinterpretiert werden — immer `bash -lc 'cd <repo> && nix … run nixpkgs#home-manager -- switch --flake /absoluter/pfad#<user>@<host>'`.
- git als root über ein User-Repo: „detected dubious ownership" → `runuser -u <user> -- env HOME=/home/<user> git config --global --add safe.directory <pfad>`. Bei JEDEM runuser ohne `-l` bleibt HOME=/root: git liest /root/.git (Permission denied), ssh-Keys und git-config des Users werden nicht gefunden — runuser-Aufrufe immer mit `env HOME=/home/<user> GIT_SSH_COMMAND="ssh -o StrictHostKeyChecking=accept-new"` (known_hosts des Users ist auf neuen Maschinen leer).
- Die darwin-pi-sync-Derivation unterscheidet sich von der Linux-Version (LaunchAgent statt systemd-Teil) → ihr nix-store-Hash weicht vom Linux-Hash ab, das ist kein Fehler. Guard-Präsenz per `grep -c "cmp -s" "$(readlink -f "$(which pi-sync)")"` prüfen, nicht per Hash-Vergleich.
- Automatisierte stille Pulls (`pull -q`, Auto-Upgrade/Sync) können einen Rebase-State stranden lassen: `.git/rebase-merge` enthält NUR `autostash`, Status meldet „all conflicts fixed: run git rebase --continue", Haupt-Branch steht schon auf origin. Erst Verlustprüfung (`git diff <autostash-sha>^1 <autostash-sha>` für Stash-Inhalt, `git diff <replay-commit> main --stat` für echten Inhalt), dann `git rebase --quit` (rührt Working Tree nicht an, wandelt Autostash in normalen Stash-Eintrag) und den Stash nach Prüfung droppen — bei leerem Replay-Patch ist er wertlos.
