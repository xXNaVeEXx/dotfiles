# Pi-Verteilung über nix-conf + dotfiles

Architektur: nix-conf installiert Pi (Flake-Input `github:earendil-works/pi/stable`) via `myHome.pi.enable` auf allen Gamzat-Maschinen; `pi-sync` spiegelt den konfigurierbaren Slice von `~/.pi/agent` über den dotfiles-Klon `~/projects/dotfiles` (Subtree `pi/`) per Git.

## Beteiligte Stellen
- `~/projects/nix-conf/flake.nix`: Input `pi` (follows nixpkgs), wird via `extraSpecialArgs`/`specialArgs` an home-module durchgereicht (3 Stellen: mkHomeLinux, nixos, darwin).
- `~/projects/nix-conf/home/modules/pi.nix`: Paket + `pi-sync`-Skript + systemd-User-Timer (nur Linux, darwin nur Skript+Activation) + Bootstrap (Erst-Pull wenn `~/.pi/agent/skills` leer).
- `~/projects/nix-conf/home/options.nix`: `myHome.pi.enable` (mkEnableOption-Muster des Repos).
- Enables: `home/gamzat-cachyos.nix`, `gamzat-shared.nix`, `gamzat.nix` (nixos), `gamzat-darwin.nix`, `home/gamzat-omarchy.nix` (aarch64-Asahi, `gamzat@omarchy`, Repo `~/projects/nix-conf`). maga/marv kriegen Pi NICHT.
- dotfiles-Repo `github:xXNaVeEXx/dotfiles`: Subtree `pi/` = AGENTS.md, settings.json, keybindings.json, skills/, extensions/ (OHNE node_modules — Symlink-Farm, regenerierbar), hermes-mind/{MEMORY.md,USER.md,config.json}.

## Sync-Umfang (was bewusst NICHT reingeht)
- auth.json: Provider-Tokens, bewusst pro Maschine → 1× `/login` je Machine (sops-Ausbau wäre später möglich, age-Key fehlt bisher auf Maschinen).
- Lokal/riesig/regenerierbar: npm/ (1012M, aus settings.json via `pi install`), install/, sessions/, backups/, ext-dev/, missions/, usage-history/, web-search-cache/, models-store.json, *.log, sessions.db*.

## Prozedur: Änderungen an der Verteilung
1. dotfiles: /tmp-Klon aktualisieren (`git pull`), pi/-Subtree ändern, Branch + Conventional-Commit, landen via `GIT_BIGPOWERS_LAND=1 bash <bigpowers>/scripts/land-branch.sh <branch> "<type>(scope): <subject>"` (guard-git/omp-hooks blocken Agent-Commits UND -Pushes direkt auf main — auch `git commit` alleine).
2. nix-conf: Modul/Option/Enables ändern, NEUE DATEIEN ZUERST `git add`en (Flake-Evaluation sieht nur getrackte Dateien — sonst „Path … is not tracked by Git"), dann Branch + land-branch.
   - land-branch-Requirements: Branch VOR dem Commit mit `git checkout -b <name>` anlegen (ein Commit direkt auf main lässt land-branch mit „Feature branch does not exist" abbrechen), Branch muss auf aktuellem origin/main basieren (sonst „not based on current main" → rebase), Commit-Subject ≤ 72 Zeichen (guard-git blockt sonst den Commit), Working Tree auf main muss clean sein → nicht-branch-Dateien vorher `git stash push -m … <dateien>`, nach dem Land `git stash pop`.
3. Rebuild je Machine: `cd ~/projects/nix-conf && home-manager switch --flake .#gamzat@cachydeck` (macbookpro: darwin-Rebuild; shared/gamzat-dev: `.#gamzat@shared`).
4. Verifikation: `which pi` IN DER LOGIN-SHELL DES NUTZERS (`zsh -ic 'whence -v pi'` — Agenten-bash hat anderen PATH, siehe mise/Bun-Stolperfalle), `pi-sync` einmal manuell, `systemctl --user list-timers pi-sync.timer` (darwin: `launchctl list | grep pi-sync`), Klon-Status `git -C ~/projects/dotfiles log --oneline -1`. Gedächtnis-Gleichstand über Maschinen per Hash beweisen, nicht annehmen: `md5sum` (Linux) bzw. `md5 -q` (macOS) über `~/.pi/agent/hermes-mind/{MEMORY.md,USER.md,config.json}` lokal und via SSH vergleichen.

## Zwei GitHub-Accounts (Firma vs. privat)
- Struktur: SSH-Host `github.com` = Firmen-Key (MaGTechDev, `identity.sshKey`), Alias `github-navee` = Privatkonto xXNaVeEXx (Option `myHome.identity.privateSshKey`, Key `~/.ssh/id_ed25519_navee`; `home/modules/ssh.nix` generiert daraus den matchBlock `github-navee`, gesetzt pro Host wo der Key liegt). Private Repos (dotfiles, nix-conf) mit Remote `git@github-navee:xXNaVeEXx/<repo>.git`; Firmen-Repos (MaG-TechOrg) unverändert über github.com. Git-Autoren-Identität: global privat, `identity.workGitDirs` (includeIf → `~/.config/git/work.conf`) setzt die Firmen-Identität nur in Firmen-Checkouts.
- SSH-Host-Aliase NIEMALS manuell in `~/.ssh/config` pflegen: `programs.ssh` (mit `enableDefaultConfig = false`) überschreibt die Datei bei JEDEM home-manager switch komplett — manuelle Aliase/IdentityFile-Zeilen sterben lautlos, danach scheitern alle Remotes der Form `git@github-navee:…` mit „Could not resolve hostname" (DNS-Fehler statt Auth-Fehler) und pi-sync/Dotfiles-Pulls brechen still. Alias IMMER als Option + matchBlock in `home/modules/ssh.nix` bauen; eine Remote-Umstellung auf einen neuen Host-Alias erst NACH dem Switch vornehmen, der den Alias deployt (Henne-Ei), oder einmalig per `git -c core.sshCommand="ssh -i <key> -o IdentitiesOnly=yes"` pullen.
- HTTPS-Remotes auf xXNaVeEXx-Repos umstellen (`git remote set-url origin git@github-navee:…`), sonst pusht der gh-credential-helper mit dem Firmen-Token und scheitert an push:false.
- SSH-Key auf Maschinen kopieren: danach `.pub` aus dem Private-Key regenerieren (`ssh-keygen -y -f <key> > <key>.pub`) — ein inkonsistentes Paar (alte .pub daneben) meldet „Permission denied (publickey)" trotz korrektem Private-Key; Verifikation nur über `ssh -vT` („Offering public key" + „Authenticated").
- Home-Manager git-Modul: `programs.git.extraConfig` ist entfernt → `settings` nutzen. settings mit bedingten includeIf-Blöcken NUR via außenliegendem `lib.mkMerge` bauen (`settings = lib.mkMerge [ base (optionalAttrs … (mkMerge (map …))) ]`) — ein `//`-Merge über einen mkMerge-Wert lässt ganze Sektionen ([user]) aus der generierten gitconfig verschwinden. includeIf-Eintrag via `lib.setAttrByPath [ "includeIf" "gitdir:<dir>" ] { path = …; }` (settings-Typ erlaubt keine Liste von Attrsets).
- Commit-Identität temporär setzen, wenn die global gitconfig gerade (noch) nicht deployt ist: `git -c user.name=… -c user.email=… commit …`.
- cachydeck-Key-Lage: `mydevkey` = PRIVATER Key (der github.com-Default dort authentifiziert als xXNaVeEXx!), Firmen-Key liegt als `github_magtechdev` herum, privater Zweitkey `id_ed25519_navee` ist kopiert (`.pub` regeneriert). Firmen-Repos per SSH sind dort erst konsistent, wenn `identity.sshKey` auf `github_magtechdev` umgestellt wird — bis dahin laufen Firmen-Git-Zugriffe dort über gh CLI/HTTPS.

## Stolperfallen
- Neue .nix-Datei untracked → Flake-Fehler beim switch: Datei VOR der Evaluation `git add`en.
- `which pi`-Verifikation pro LOGIN-SHELL machen, nicht im Agenten-Kontext: Legacy-Installer können `~/.local/bin/pi`-Wrapper (z. B. mise → Bun-kompilierter pi) VOR `~/.nix-profile/bin` in den User-PATH schieben. Bun-Binaries laden KEINE TS-Extensions: jiti importiert sie als `data:text/javascript;base64,…`-URL, Bun wirft `ResolveMessage: NameTooLong … from '/$bunfs/root/pi'` (jitis ENAMETOOLONG-Tempfile-Fallback erkennt Bun-Fehlercodes nicht) → „Failed to load extension …error-hub.ts" direkt beim Start, obwohl der Nix-pi (Node-basiert) dieselben Extensions sauber lädt. Fix: Wrapper sichern (`mv ~/.local/bin/pi ~/.local/bin/pi.mise-wrapper.bak`) + `mise unuse -g pi` (sonst zieht ein `pi = "latest"`-Pin den Bun-pi bei nächster Gelegenheit wieder nach). Repro pro Binary: `<pfad>/pi -p ok`; Fingerprint `$bunfs` im Fehlerpfad = Bun-Binary.
- `mkHomeLinux` ist inzwischen system-parameterisiert (`mkHomeLinux "aarch64-linux" ./home/gamzat-omarchy.nix` existiert) — bei neuen Hosts einfach den System-String übergeben; ein harter `legacyPackages.x86_64-linux`-Pin würde aarch64-Hosts verfälschen/brechen.
- Pro-Host Paket-Abschaltung: `home/profiles/*.nix` setzen `myHome.apps.<name> = true` als Default; Abschalten pro Host nur per `lib.mkForce false` in `home/gamzat-<host>.nix` (zwei plain Definitionen mergen nicht). Geänderte GETRACKTE Dateien sieht der Flake auch uncommittet → `home-manager switch` aus dem Working Tree funktioniert für schnelle lokale Fixes. Falle: Die App-Option koppelt Paket UND Dotfile-Deployment (apps.nix) — `mkForce false` entfernt beim Switch auch die bereits deployte Config (z. B. `~/.config/wezterm`), Anwendungen starten mit Defaults. Config trotzdem behalten: Function-Head des Host-Files um `dotfiles` erweitern und selbst `home.file.".config/<app>" = { source = "${dotfiles}/<app>"; recursive = true; };` deployen.

## Neue Maschine komplettieren (Dotfiles-Deckung)
1. Lücken-Audit: Repo-Dirs des dotfiles-Inputs (derzeit fish, nvim, pi, tmux, wezterm, zsh) gegen Deploy-Sites prüfen (`grep -rn 'home.file\|xdg.configFile' nix-conf/home/`) und gegen Live-`ls` im Home. Dirs ohne Deploy-Site (z. B. fish) als unconditional Modul nach dem dotfiles-base-Muster ergänzen (`home/modules/<name>.nix` mit `home.file.".config/<dir>"`, Import in `modules/default.nix`), neue Datei vorher `git add -N` (Intent-to-add reicht für Flake-Sichtbarkeit).
2. Deploy ≠ aktiv: Login-Shell prüfen (`getent passwd <user>` — kann bare /bin/bash sein, obwohl zsh-Config längst deployt ist). Auf Nicht-NixOS aktivieren: `printf '%s\n' /home/<user>/.nix-profile/bin/zsh | pkexec tee -a /etc/shells` + `pkexec chsh -s /home/<user>/.nix-profile/bin/zsh <user>` (nix-profile-Symlink statt Store-Pfad: stabil über Generationen). Verifikation: `zsh -i -c 'echo ok'` — Erstlauf bootstrapped zinit/p10k mit.
   - Session-Env-Vererbung verstehen: `systemctl --user set-environment SHELL=… && dbus-update-activation-environment --systemd SHELL=…` wirkt NUR auf via systemd/DBus gestartete Prozesse. GUI-Terminals sind Kinder des Compositors (Hyprland & Co.) und erben dessen LOGIN-Env — ein Shell-Wechsel nach dem Login erreicht sie erst nach Neu-Anmeldung. Effektive Env beweisen: `tr '\0' '\n' < /proc/$(pgrep -x Hyprland)/environ | grep ^SHELL`. Deterministischer Sofort-Fix ohne Re-Login: explizite Shell im Terminal-Config setzen (z. B. `shell=` in `~/.config/foot/foot.ini`, `default_prog` in wezterm.lua).
3. Secret-Scan vor dem Deploy: das dotfiles-Repo ist public — Klartext-Keys in Config-Dirs (`grep -rn 'sk-\|API_KEY'`) dem User zum Rotieren melden, nicht kommentarlos weiterverteilen.
4. Auto-Install-Blöcke in deployten RC-Dateien (.zshrc & Co.) loopen: die RC ist ein read-only Store-Symlink, der Installer kann seinen Source-String nie persistieren → er läuft bei JEDEM Shell-Start erneut (Downloads, Init-Noise, p10k-instant-prompt-Warnung). Fix-Muster ohne RC-Änderung: das erwartete Tool an den Pfad legen, den die RC prüft (Guard wird still übersprungen). Shell-Init-Stille nur MIT pty verifizieren (`script -qec "zsh -i -c exit" /dev/null`) — `zsh -i -c` ohne tty erzeugt gitstatus/setopt-Artefakte, die echte Fenster nicht haben.
- land-branch nicht anstoßen, wenn lokales main Commits vor origin/main hat: der Branch müsste darauf basieren und schiebt die fremden Commits mit → Working-Tree-Fix + Switch machen, Landen mit dem User klären.
- bg_run/bash-Ketten verschlucken den Exit-Code des überwachten Befehls, wenn ihm ein weiteres Statement folgt: `| tail` liefert tail-RC, und `…; echo "EXIT=$?"` macht den Task-Exit IMMER 0 — die bg-Notification meldet dann „exit-code 0" trotz Fehlschlag. → Den überwachten Befehl als letztes Statement laufen lassen oder das echte Ergebnis NUR aus der Log-Tail (EXIT-Zeile/Fehlermeldung) lesen, nie aus der Task-Notification.
- Erstlauf von pi-sync klont nach `~/projects/dotfiles`; schlägt SSH fehl, exitiert er still (Timer retryt). /tmp/dotfiles ist NICHT der Sync-Klon.
- Push-Rechte separat prüfen: Alle Gamzat-Maschinen authentifizieren als MaGTechDev (SSH-Key + gh CLI), das dotfiles-Repo gehört aber xXNaVeEXx. Stand 23.10.2026: `gh api repos/xXNaVeEXx/dotfiles --jq .permissions` = pull:true, push:false → JEDER push (auch pi-sync-Timer und land-branch) scheitert still mit „Permission to xXNaVeEXx/dotfiles.git denied to MaGTechDev"; local main häuft unpushete Auto-Sync-Commits an. Dauerfix nur durch User: als xXNaVeExx MaGTechDev als Collaborator (Write) hinzufügen. Bis dahin: Fixes auf Safety-Branches parken.
- pi-sync-Schritt 2 macht `git reset --hard origin/main`, sobald HEAD != origin/main — alle 20 min! Uncommittete Änderungen AUSSERHALB von pi/ im dotfiles-Klon werden kommentarlos verworfen, unpushete main-Commits werden dangling. Schutz: Änderungen sofort auf einen Branch committen (Timer fasst nur main an) + `git bundle create /tmp/dotfiles-pending.bundle <branch>` als Backup. Nach einem solchen Verlust: Commits hängen noch im Reflog/dangling (`git reflog`, alte Hashes prüfen).
- `home-manager switch --override-input dotfiles /home/gamzat/projects/dotfiles` evaluiert den ARBEITSBAUM des Klons. Rennen Switch und pi-sync-Timer in dieselben Minuten, bricht die Evaluation mit „error: path '…/pi/skills/…/SKILL.md' does not exist" (Reset hat Dateien gerade entfernt, rsync lädt sie neu). Einfach NACH dem Timer-Lauf neu starten; einmal aktiviert ist der Deploy ein unveränderlicher Store-Pfad und gegen spätere Resets immun.
- Rebuilds im Hintergrund (bg_run) in nix-conf: der Dirty-Tree-Prompt von `rebuild.sh` (`read -n 1`) exitet ohne TTY sofort mit RC 1, Log zeigt nur die Warnzeile → `printf 'y\n' | ./rebuild.sh …` voranstellen. Danach scheitert darwin `switch` an sudo ohne Passwort-TTY (tty_tickets verhindert Vorab-Caching) → im Hintergrund stattdessen sudo-frei `darwin-rebuild build --flake .#<host>` validieren und die Aktivierung dem User-interaktiven `./rebuild.sh switch` überlassen (Home-Manager-only-Ziele auf Linux brauchen kein sudo und laufen komplett im Hintergrund durch).
- pi-sync überschreibt lokale Divergenzen im Sync-Slice im Last-Pusher-Wins-Verfahren; Git-Historie im Klon bleibt Rückgrat.
- Timer-Service läuft ohne TTY/Agent: git push kann ohne SSH-Agent scheitern — toleriert, nächster Lauf retryt.
- Rückroll-Gefahr: Eine Maschine mit altem Live-Stand kann ältere Inhalte über neuere Commits pushen. Ursache war der mtime-only-Guard: Er las Pull-Echos als lokale Änderungen (Schritt 5 rsync -a setzt Live-mtimes auf Pull-Zeit). Fix: cmp-Inhaltsvergleich im Push-Teil (fe429f4); Maschinen ohne Rebuild haben noch das alte pi-sync und können weiter zurückrollen.
  - Nach eigenen Skill-/Memory-Änderungen den nächsten Timer-Lauf (~20 min) abwarten und prüfen: `git -C ~/projects/dotfiles log --format='%h %an %ad %s' --date=format:%H:%M -8 -- pi/skills/<name>` (Commit einer anderen Maschine nach meinem?) und die neue Zeile per `grep` in der Live-Datei. Fehlt sie, über skill_manage neu einspielen.
  - Nach einem Rückroll jede eigene Änderung einzeln prüfen, nicht nur die auffälligen. Grund: Wiederherstellungs-Commits übersehen leicht einzelne Dateien.
  - Beim Manuell-Arbeiten im Klon: immer ERST Live reparieren, DANN Klon (sonst überschreibt der nächste Timer-Lauf den Klon-Stand mit dem alten Live-Stand).
- In nix writeShellScriptBin (''-Strings) ist `read -d ''` ein Syntaxbruch (`''` startet nix-Escape) → `'''` schreiben (5e3f7b6).
- Schlägt eine HM-Aktivierung nach „remove home-manager-path" fehl (z. B. File-Kollision wie manuelles `nix profile install gh` vs. gh-Modul), ist das home-manager-Binary selbst weg und `nix profile rollback` scheitert (Generation 0) → Rettung: `nix run nixpkgs#home-manager -- switch --flake .#<host>`. Darwin-Activation braucht ROOT: `sudo darwin-rebuild switch --flake .#macbookpro` (remote ohne Passwort nicht automatisierbar).
- Repo-Pfad ist maschinenabhängig (darwin: `~/nix-config`, andere: `~/projects/nix-conf`) — Pfad am Live-System verifizieren, nie blind aus diesem Skill übernehmen.
- Git-Push fragt nach Login und scheitert mit „authentication failed" → Repo hängt an HTTPS-Remote; GitHub nimmt Passwort-Auth nicht mehr an. Diagnose: `git remote -v` + SSH-Test `ssh -T git@github.com` (erwartet: „Hi <user>!"), Fix: `git remote set-url origin git@github.com:<user>/<repo>.git`. Bei mehreren Klonen pro Maschine jedes Repo einzeln prüfen.
- Die darwin-pi-sync-Derivation unterscheidet sich von der Linux-Version (LaunchAgent statt systemd-Teil) → ihr nix-store-Hash weicht vom Linux-Hash ab, das ist kein Fehler. Guard-Präsenz per `grep -c "cmp -s" "$(readlink -f "$(which pi-sync)")"` prüfen, nicht per Hash-Vergleich.
- Automatisierte stille Pulls (`pull -q`, Auto-Upgrade/Sync) können einen Rebase-State stranden lassen: `.git/rebase-merge` enthält NUR `autostash`, Status meldet „all conflicts fixed: run git rebase --continue", Haupt-Branch steht schon auf origin. Erst Verlustprüfung (`git diff <autostash-sha>^1 <autostash-sha>` für Stash-Inhalt, `git diff <replay-commit> main --stat` für echten Inhalt), dann `git rebase --quit` (rührt Working Tree nicht an, wandelt Autostash in normalen Stash-Eintrag) und den Stash nach Prüfung droppen — bei leerem Replay-Patch ist er wertlos.
- Push-Erfolg nie aus lokalen Refs schließen: `git rev-parse origin/main` / `git log origin/main` zeigen die LOKALE Tracking-Ref, auch wenn der Push längst scheiterte — und land-branch meldet „Land complete" ohne Push-Beweis. Remote-Wahrheit per `git ls-remote <remote> main` oder `gh api repos/<owner>/<repo>/commits/main --jq .sha` verifizieren.
- Pi-Update-Prozedur: `stable`-Branch des pi-Flakes hinkt Releases hinterher (moving branch, kann hunderte Commits hinter dem neuesten Tag stehen) — Zielversion per `git ls-remote --tags` bestimmen; `package.json` version ist bei pi KEINE Versionsquelle, nur `pi --version` des installierten Binarys. Release-Tags können unter Nix kaputt sein: ein workspace-package-lock ohne `integrity`-Felder lässt nixpkgs' import-npm-lock mit „attribute 'integrity' missing" abbrechen (egal ob pi unserem nixpkgs folgt oder sein eigenes mitbringt). Deshalb VOR dem switch die Evaluation testen (`nix eval .#homeConfigurations.<host>.config.home.activationPackage.drvPath --raw`); bricht der Tag, auf den gefixten main-HEAD pinnen (volle sha im Input-URL: deterministisch, kein moving target).
