# lumi-desktop-local-builds

# Schwere Builds/Tests und dsh-Runtime-Proben für apps/lumi-desktop LOKAL

Anwenden, wenn Builds, Tests oder dsh-Kompatibilitäts-Proben für apps/lumi-desktop laufen sollen — lokal oder auf dem Remote-Testrechner — oder wenn eine Sitzung vom Ausgabe-Wächter per SIGTERM getrennt wurde und lange Befehle nach dem Resume weiterlaufen müssen.

## 0 Remote zuerst (RAM-Schonung)
- Schwere UI-Suiten/Builds bevorzugt über `apps/lumi-desktop/tools/remote.sh pnpm|cargo|sh …` auf dem Remote-Rechner laufen lassen (Host-Default per `LUMI_REMOTE_HOST`, aktuell das Asahi-MacBook „omarchy" mit Linux aarch64 → Nix-Shell `devShells.aarch64-linux.desktop`; rsync nach `~/lumi-remote`). Lokal nur bei Exit 75 (Host nicht erreichbar) oder x86_64-Spezifischem.
- Neuer/neu installierter Remote-Host: erst `tools/remote.sh pnpm install --frozen-lockfile`, dann eine kleine Probe (`tools/remote.sh pnpm exec vitest run src/ui`) bevor die Gesamtsuite dorthin geht. Der Zielordner muss vor rsync existieren (`ssh host "mkdir -p \$HOME/<rbase>"` im Skript; `\$HOME` remote auswerten, SC2029 ist gewollt).
- Falsches Werkzeug auf dem Remote-Host (z. B. „rustup could not choose a version of cargo", alte clippy-Version): zuerst `tools/remote.sh sh 'type -a cargo; cargo --version'` — es muss das cargo aus /nix/store gewinnen. home-manager legt gern Shims (rustup) nach `~/.nix-profile/bin`, und Login-/rc-Dateien schieben diesen Ordner wieder VOR die Nix-Dev-Umgebung. Darum hängt `tools/remote-exec.sh` `~/.nix-profile/bin` und `~/.cargo/bin` ans PATH-Ende und startet die innere Shell mit `bash --norc --noprofile`; beim Ändern von remote-exec.sh beides erhalten.
- Ein Shell-Skript NIE editieren, während ein bg_run/Lauf es gerade ausführt — bash liest Skripte stückweise von der Platte und meldet dann Phantom-Syntaxfehler („syntax error near unexpected token )") mitten im Lauf, obwohl `bash -n` sauber ist. Erst Lauf beenden lassen, dann ändern, dann neu starten.

## 1 Grundregeln (je Schritt)
- cargo NUR über `apps/lumi-desktop/tools/cargo-safe.sh`, pnpm NUR über `tools/pnpm-safe.sh` (beide: flock auf `<repo>/.tmp/cargo-build.lock`, systemd-run MemoryMax, TMPDIR auf Platte, Nix-Shell `.#desktop`).
- Immer nur EIN schwerer Schritt gleichzeitig; vorher `free -m` (verfügbar > 3 GB). Nie cargo und pnpm parallel.
- Ausgabe nach `<repo>/.tmp/<name>.log` (absolute Pfade! `/tmp` ist RAM — nichts Großes dorthin), nur `tail` lesen.
- Echtes dsh braucht offizielles Node: `PATH=$HOME/.nvm/versions/node/v24.21.0/bin:$PATH`.

## 2 Wächter-Schleife für lange Befehle (Ausgabe-Wächter tötet stille Sitzungen)
Nie länger als ~10 Minuten ohne eigene Ausgabe. Statt eines blockierenden Aufrufs:

```bash
R=/absoluter/repo/pfad
setsid nohup bash -c "cd $R/apps/lumi-desktop && timeout 1500 tools/cargo-safe.sh <ziel> > $R/.tmp/<name>.log 2>&1; echo \"EXIT=\$?\" >> $R/.tmp/<name>.log" >/dev/null 2>&1 &
sleep 90; tail -n 3 $R/.tmp/<name>.log   # wiederholen bis EXIT=… im Log steht
```

Stolperfallen:
- Das bash-Tool des Agenten tötet beim Return die ganze Prozessgruppe — `& disown` allein reicht NICHT, der Hintergrundjob stirbt still. `setsid` löst die Gruppe; ohne Nachweis im Log gilt der Lauf als nicht gestartet.
- Präzedenz-Falle: `cd X && cmd &` hintergrundet die GESAMTE Kette; Befehle nach `;`/neue Zeile laufen im alten cwd → relative Pfade (`../../.tmp`) zeigen dann ins Leere und simulieren einen Fehlschlag. Immer absolute Pfade für Log-Checks, oder `cd` vor dem `&` in einem eigenen Schritt.
- Diagnose, bevor something als „läuft nicht" gilt: `pgrep -af <prozess>` und `ls` auf den Log-Pfad mit absolutem Pfad. ripgrep-Falle: `rg -rn "muster"` ist NICHT „rekursiv + Zeilennummern" — `-r` ist `--replace` und ersetzt jedes Match im OUTPUT durch den nächsten Buchstaben (z. B. `n`), was Pseudo-Treffer wie `lib.rs:fn n(state…` liefert. rg ist ohnehin rekursiv; Zeilennummern = `-n`, Dateiliste = `-l`. Keine Dateien werden verändert, aber Diagnose-Outputs werden korrumpiert — bei wirren rg-Ergebnissen zuerst die Flags prüfen.
- Poll-Wächter über API-Status (CI-Checks, PR-Rollup): Abbruch-/Erfolgbedingung erst prüfen, wenn das Ziel-Objekt überhaupt registriert ist (Checks-Anzahl > 0) — direkt nach dem Erstellen ist die Rollup-Liste leer und „alle grün" trifft auf die LEERE Liste zu, ein Wächter mit `grep done:0 || … && break` bricht sofort ab. Shell-Präzedenz explizit klammern: `a || b && c` wertet als `(a || b) && c`.

## 3 dsh-Kompatibilitäts-Proben (z. B. Plugin vs. Runtime-Pin)
1. `tools/compat-fetch.sh --neueste` → Cache `~/.cache/lumi-compat-neueste` (Plugins @HEAD, `versions.tsv` listet Commits). npm-Downloads ok; nichts in `~/.cache` löschen.
2. Vor jeder Probe das dist des Hosts prüfen: `ext-host-dsh/dist` veraltet gern gegen `src` (tsc-Zeitstempel vergleichen). Neu bauen mit offiziellem Node: `node_modules/.bin/tsc -p tsconfig.json && node_modules/.bin/tsc -p bridge/tsconfig.json` — sonst fehlen neue RPC-Handler (z. B. `plugin/bundles`) und die Probe scheitert an phantom-Fehlern.
3. Treiber-Muster (Node-Skript, Vorlage `.tmp/p8k-load.mjs`): `dist/src/main.js` spawnen mit `--dsh-home <tmp> --plugin <dir> --cwd <basis> [--web]`, dann über stdin/stdout-JSON-RPC `host/initialize` → `plugin/list` pollen → `plugin/bundles` (skippedBundles). Ausnahme erteilen = `profiles/lumi/compatibility.json` mit `{"<name>@<version>": ["<runtime>"]}` vor dem Start schreiben.
4. Runtime-Seite testen OHNE Repo-Pins zu ändern: Host-Kopie im Cache-Baum anlegen (src + tsconfigs kopieren, package.json mit sed auf die Zielversion), dort `npm install`. Stolperfalle neuere dsh-Stände (≥ 0.2.1): sie erkläern ~100 `@deepseek-ai/*`-Pakete als echte peerDependencies statt sie zu bündeln — `--legacy-peer-deps` installiert die NICHT, der Host stirbt erst zur Laufzeit an `ERR_MODULE_NOT_FOUND`. Abhilfe: per Node-Skript über `node_modules/@deepseek-ai/*/peerDependencies` die fehlenden sammeln und in EINEM `npm install peer@range …` nachziehen.
5. Erwartungsbilder: ohne Ausnahme + alte Runtime → Bundle in `skippedBundles`, `plugin/list` zeigt es nicht; mit passender Runtime (oder Ausnahme) → `state:"active"` (mit `--web`; ohne web bleibt es `pending`, wartet auf webServer — kein Fehler).

## 4 Abnahme durch Orchestrator nach Worker-Abschluss (vor jedem Commit)
Worker enden gern KURZ vor den finalen Läufen (Watchdog/Timeout) — „fertig" heißt erst fertig nach eigener Verifikation. acp-Worker haben ein 30-Min-Hard-Limit: Brief so gestalten, dass Code+Tests zuerst kommen, LÄUFE am Ende gebündelt und der Bericht früh/fortlaufend geschrieben wird. Brief-Pfad-Regel: alle Datei-Pfade im Brief voll repo-relativ qualifizieren (z. B. `apps/lumi-desktop/docs/reports/P9x-….md`, nie nur `docs/reports/…`) — Worker mit cwd=Repo-Root legen relative Pfade sonst im Root an; nach Worker-Ende `git status` auf untracked `docs/`-Ordner am Root prüfen und Fehlplatziertes verschieben. Nach einem Timeout: Waisen-Läufe prüfen (`pgrep -af cargo`), Log-Stand auswerten (`Finished`/`error`), dann Resume mit diesem KONKREten Zwischenstand füttern (nicht pauschal „mach weiter").
1. Bericht auf Platzhalter prüfen: `grep -n "folgt nach\|TODO\|⟨" docs/reports/<paket>.md` — leere Test-Abschnitte selbst füllen.
2. Selbst verifizieren (je ein schwerer Schritt): `tools/cargo-safe.sh nextest run -p <betroffene crates>` → `tools/cargo-safe.sh clippy -p <crates> --all-targets -- -D warnings` → aus `ui/`: `../tools/pnpm-safe.sh test`. Berichts-Abschnitt „Tests" mit diesen EIGENEN Zahlen füllen (plus Hinweis auf Orchestrator-Fixes). Test-Zahlen NIE schätzen oder aus Erinnerung eintragen — Zeile für Zeile aus dem echten Log kopieren (zählbare Summen wie „198 Dateien / 1084 Tests" wurden schon zweimal um genau 1 daneben geschätzt und mussten nach dem Lauf korrigiert werden). Wartet ein Worker auf einen eigenen Hintergrund-Verifikationslauf, MUSS er ihn pollend begleiten (sleep+tail-Schleife) — stilles Warten triggert den Ausgabe-Wächter, und der bg-Lauf stirbt mit dem Worker (Prozessgruppe). Ist die Teilarbeit bei Timeout trotzdem komplett implementiert, übernimmt der Orchestrator die Schlussverifikation selbst — billiger als ein Resume-Zyklus.
3. Typische Restfixe nach Workern: fehlende i18n-Keys → in `i18n/desktop/coding.en.json`/`coding.ru.json` per Python (`ensure_ascii=False`, Key = deutscher Quelltext) ergänzen — Fehljobs aus der VITEST-Ausgabe lesen (`grep -A12 "Failed Tests"`), keine eigene Regex-Replik über Quelltext bauen (matcht mehrzeilig falsch). UI-Selektor-Regel: Tests niemals positionale DOM-Selektoren („erstes div im Container", `> div` auf Indexbasis) asserting — kommt ein weiteres Kindelement dazu (z. B. Karte zusätzlich zum Spotlight-Loch), matcht der Selektor das falsche Element; dem zu prüfenden Produktions-Knoten einen eigenen `data-testid` geben und den Test darauf umstellen. Clippy `must_use`-Reste → `let _ =` vor den Aufruf. Rust-Struct-Felder ohne Default brechen ALLE Struct-Literal-Initializer im Workspace — auch Tests älterer Pakete; nach Feld-Erweiterungen (z. B. an ThreadRecord-artigen Records) die Test-Initializer überall nachziehen, sonst fliegt der Kompilierfehler erst beim nächsten Paket-Lauf auf.
   - Serde-Kontrakt-Regel für JSON-API-Structs (Rust→UI/TS): verlangt der Kontrakt „fehlende Optionale werden weggelassen", brauchen Option-Felder `#[serde(default, skip_serializing_if = "Option::is_none")]` — ohne das serialisiert serde `"feld": null` und Kontrakt-/Snapshot-Tests schlagen fehl, obwohl die Deserialisierung klaglos läuft. Geteilter-Irrtums-Falle: Worker-Komponente UND deren Test-Helper bauen gern dieselbe falsche Datenform (z. B. verschachtelte Diskriminanten-Objekte statt flacher String-Tags) — Suite läuft grün gegen den Mock und bricht trotzdem gegen echte Daten. Richte beide Seiten am GENERIERTEN Kontraktstyp aus (ui/src/generated/…); Test-Factory per Spread ({...base, ...state}) bauen, nicht per Feldzuweisung.
   - Display-only-IPC-Feld-Muster (abgeleiteter Wert ohne Persistenz-Drift, z. B. „effektiver" Wert über einem leer=Default-Rohfeld): Feld im Kontrakt als `Option<String>` mit `#[serde(skip_deserializing, default, skip_serializing_if = "Option::is_none")]` + `#[ts(optional)]`; der IPC-Wrapper (z. B. settings_payload) setzt es beim LESEN, alle Schreibpfade nie. Zwei Pflicht-Absicherungen: (a) UI-Echos des Feldes fallen beim Einlesen als unbekannter Schlüssel ins flatten-`extra` → vor dem Speichern entfernen (`settings.extra.remove("<key>")` im Setter), sonst landet der Anzeigewert in der Datei; (b) pasted Default-Texte im Rohfeld normalisieren (leerer String) statt als Nutzer-Override zu persistieren. Dart-/Mobile-Persistenz und Rust-Sicht teilen sich dieselbe Datei — nur das Rohfeld ist Vertrag, die Ableitung nie.
   - Rust-E0716-Regel für Worker-Restfixe: `let Some(x) = expr.chain().as_ref() else …` kompiliert NICHT, wenn `expr.chain()` ein Temporäres liefert und `x` erst im NÄCHSTEN Statement genutzt wird (Temporäre fallen am Ende des let-Statements). Vor dem let-else ein `let owned = expr.chain();` binden und darauf `as_ref()` nehmen. Ein-Ausdruck-Ketten (`Some(x.chain().y().await)`) sind ungefährdet, weil Nutzung im selben Statement steht.
   - Bibliotheken übersetzen HTTP-Statuscodes in eigene Meldungen: stringbasierte Fehler-Erkennung (z. B. 401→Refresh) auf den LIBRARY-Text der unwrap-ten Fehlerkette testen, nicht nur auf den HTTP-Code — rmcp meldet 401 als „Auth required, when send initialize request", ohne jede Ziffer. Beim Ergänzen neuer Matcher die konkrete Meldung aus dem Test-Fail-Panik kopieren.
   - Beispiel-/Testserver (z. B. mini_mcp_server): neue Auth- oder Guard-Layer gehören HINTER das auslösende Flag — axum-Layers greifen für ALLE Starts, auch ohne Flag, und 401n dann jede bestehende Testnutzung, die das Flag nicht setzt. Ebenso RFC-9728-Gedenke: `/.well-known/*`-Metadaten müssen Guard-frei bleiben (Guard-Layer nimmt Pfad-Weiche VOR der Token-Prüfung), sonst findet der Client den Authorization-Server nie.
   - i18n-Heimat-Regel: jeder Key lebt GENAU EINMAL in seiner Paket-Datei (z. B. `coding-p9d.{en,ru}.json`); Duplikate in `coding.{en,ru}.json` feuern den en↔ru-Gleichheits-Test. Beim Entfernen per `sed` Zeile N prüfen: war sie der letzte Eintrag, hängt ein trailing comma (`",\n}` → `"}`) — danach `json.load` validieren.
   - Vite-Transform-Cache-Falle: meldet ein Test Keys/Bereichs-Mocks als fehlend, die nachweislich in den Dateien stehen (import.meta.glob wird beim TRANSFORMIEREN der nutzenden Datei zu statischen Imports expandiert; ein stale Artefakt hält den alten glob-Stand): Datei beliebig anfassen (auch eine Kommentar-/`void 0;`-Zeile erzwingt Neu-Transformierung) oder `node_modules/.vite` löschen. Beweis-Trick: syntaktisch wirkungslose Zeile einfügen → wird's grün, ist es der Cache, nicht der Datensatz. Gilt für Datei-Globs (i18n-JSONs) WIE Ordner-Globs (z. B. `ui/src/*/mock.ts` in mock-install.ts — ein NEUER Bereichsordner wird phantom-artig übersehen). Strukturelle Abhilfe: Verzeichnisliste per `node:fs` + dynamisches `await import()` statt glob; dabei (a) Funktion wird async → alle Aufrufer (test-setup, main.tsx) müssen awaiten, (b) in jsdom/vitest ist `import.meta.url` http://localhost/…, URL-Konstrukte für fs schlagen an „The URL must be of scheme file" → cwd-relative Pfade nehmen und mit einem fs.existsSync-Selbsttest auf die eigene Quelldatei zwischen Test-/Node- (nutzt fs) und Browser-Vorschau (glob-Fallback im try/catch) unterscheiden, (c) Ordner ohne Zieldatei per existSync-Filter ausschließen, sonst stirbt Promise.all am Import-Fehler.
   - Neue-UI-Seite-Regel: Fügt ein Worker eine Seite in ein `ui/src/<bereich>/area.ts` (`pages: { … lazy }`) oder einen Palette-Befehl (`commands: [{ id: "cmd:…" }]`) ein, brechen VIER Stellen gleichzeitig, wenn nicht alle bedient werden — (1) Eintrag in `PAGE_ROUTES` (service.rs, test-only const; der Vollständigkeits-Test `every_ui_page_has_a_voice_route` in src-tauri/src/cmd/assistant/tests.rs liest ALLE area.ts-Dateien), (2) Arm in `route_to_navigate()` (service.rs), der auf die Seite navigiert, (3) Sprach-Alias in `DESKTOP_PAGES` (crates/lumi-logic/src/voice_control.rs), damit „öffne <name>" funktioniert, (4) Sprachsatz ODER `excluded`-Eintrag für JEDE neue Paletten-ID (`page:<mode>:<seite>` und `cmd:<…>`) in `crates/lumi-logic/data/voice_palette.json` — der UI-Test `p8a-voice-palette.test.ts` und der Rust-Test `p8a_voice_palette.rs` erzwingen beide die Abdeckung. Nach dem Hinzufügen alle vier Stellen im selben Paket ergänzen — sonst fliegen die Tests erst beim nächsten Orchestrator-Lauf auf. Zusätzlich-Kollisionsregel für Sprachsätze: ein NEUER Satz darf nicht bereits vom bestehenden Sprachparser als laufender Befehl erkannt werden (`p8a_phrases_do_not_collide_with_existing_voice_commands` prüft jeden Satz gegen parse_command) — kollidiert ein Satz (z. B. „start tour"/„tour starten" fällt unter Help{tour:true}), den Satz STREICHEN oder umformulieren, niemals den Test lockern; der Panik-Text nenmt ID, Satz und den kollidierenden Befehl. Dasselbe gilt für die Regex-Fast-Paths des Assistenten (z. B. Fehlerbericht-Erkennung in crates/lumi-assistant/src/actions/bug.rs): ein Satz, der deren Trigger enthält („… melden"), landet im Fast-Path statt in der Palette — das fängt nur der Rust-Test `p8a_voice_palette_dispatch` (lumi-assistant) ab, nicht der lumi-logic-Test. Satz umformulieren (Substantiv statt Verb-Trigger), den Fast-Path nicht verengen, weil echte Befehle ihn brauchen. Bei Glossar-/Umbenennungs-Etappen, die Synonyme in voice_palette.json ergänzen, darum beide Tests laufen lassen: `cargo nextest run -p lumi-logic -p lumi-assistant --test p8a_voice_palette_dispatch`.
   - i18n-Übersetzungs-Gleichheit: derselbe deutsche Key darf in MEHREREN Bereichsdateien vorkommen, muss dort aber IDENTISCH übersetzt sein — der Konflikt-Test (`i18n-coverage.test.ts` „gleicher Schlüssel hat in allen Bereichsdateien dieselbe Übersetzung") bricht bei abweichenden Werten (z. B. ru „Спросить" vs „Спрашивать"). Beim Anlegen eines schon existierenden Keys die Übersetzung aus der bestehenden Heimat-Datei übernehmen, nicht neu formulieren.
   - Leeres-Einstellungsfeld-Diagnose (Default-on-Load): zeigt die UI ein Einstellungsfeld leer, ist das kein Bug, wenn from_json beim Laden einen eingebauten Default substituiert und to_json den Wert nur bei ABWEICHUNG vom Default persistiert (Muster in crates/lumi-assistant/src/settings.rs systemPrompt → default_system_prompt_for(app_lang)). Kette prüfen: Rust from_json/to_json-Normalisierung + UI api.ts-Default (leerer String bei fehlendem Feld). UX-Regel: solch ein Feld braucht einen Placeholder wie „Leer lassen = eingebauter Standard aktiv", sonst melden Nutzer es als kaputt; neue t()-Strings brauchen i18n-Einträge + i18nDesktopKeys-Regeneration (Coverage-Test erzwingt).
   - Versions-Strings in generierten/statischen Assets (z. B. Handbuch-Wissensbasis) werden bei Release-Bumps stale, weil die Assets nur bei Inhaltsänderungen regeneriert werden. Anzeigen/DTOs sollen deshalb die LAUFENDE Version melden — `env!("CARGO_PKG_VERSION")` im DTO statt des Asset-Werts; Unit- UND Integrationstests desselben Pakets dürfen Versionen nicht hart verankern, sondern gegen dasselbe env! prüfen, sonst rotet der Test beim nächsten Bump. Wird der Asset-Wert trotzdem gepflegt: minimal per String-Replace ändern, NICHT mit json.dump(sort_keys=True) neu serialisieren — Re-Sortierung erzeugt bei mehrhundert-KB-Dateien Tausende Zeilen kosmetischen Diff. Ändert sich ein Asset, das ein Drift-Test byte-genau gegen die Generator-Ausgabe hält, den Generator MITLAUFEN lassen, sonst rotet der Drift-Test.
   - Diagnose „neues Feature für Bestandsnutzer unsichtbar" (z. B. geführte Touren nach App-Update): erst persistierte Einmal-Merker prüfen (etwa `tourSeen` in desktop/onboarding.json) — der Gate-Ausdruck `show && !seen` blendet nachgelieferte Features für alte Profile aus, ohne dass Code fehlerhaft wäre. Solche Features brauchen einen DAUERHAFTEN, merker-unabhängigen Zugang (eigener Tab/Karte neben dem Onboarding-Einstieg); den Zugang ergänzen statt den Merker zurückzusetzen (Bestandsnutzer wollen die Erste-Tour-Erfahrung nicht zwangsweise erneut).
4. Commit-Konvention einhalten: Subject ≤72 (Guard-Hook), deutscher Body + „Geprüft:"-Abschnitt mit Zahlen; `git add` + `git commit` ZUSAMMEN (nach Hook-Block Staging unzuverlässig); push via `.tmp/askpass.sh`. Der Guard-Hook blockt zusätzlich Direktpushs auf geschütztes main (auch reine chore-/Versions-Commits brauchen Branch + PR) und Kommandos mit `git branch -D` (Ersatz-Branch anlegen oder umbenennen statt zu löschen). Branch-Falle bei Hook-Block: lief die Kette `git checkout -b <neu> && add && commit` und blockt NUR der Commit-Hook, ist der Branch-Wechsel trotzdem durch — beim Wiederholungs-commit OHNE checkout landet der Commit auf dem VORHERIGEN Branch, und `git push -u origin <neu>` scheitert an „Src-Refspec entspricht keiner Referenz". Nach jedem Hook-Block erst `git branch --show-current` prüfen, dann ggf. `git branch -m <alt> <neu>` statt neu zu committen. Weitere Guard-Falle: lange `&&`-Ketten mit `git pull origin main`/`git push` NACH einem Guard-blockierten Kommando abreissen lassen und die Restschritte EINZELN ausführen — der Guard bewertet die ganze Kommandozeile und blockt harmlose Folgeschritte mit ab („Direct push to protected branch" auch bei reinem Pull/Tag-Push in derselben Zeile); einzeln ausgeführt laufen sie problemlos.

## 5 Abschluss
Testzahlen aus den Logs zitieren (nextest-Summary, vitest-Summary, clippy/tsc exit), Probe-Ergebnis als „Version X: active/skipped"-Paar. Für Rust: `clippy -p <crate> --all-targets -- -D warnings` zusätzlich zu nextest laufen lassen — nextest verkraftet unbenutzte Imports, clippy mit `-D warnings` nicht. Generierte UI-Dateien nur per Generator (`cargo-safe.sh export-ts` für Contracts, `node tools/i18n-desktop-keys.mjs` für i18n); Abgleich = Generator laufen lassen, `git diff` in `ui/src/generated/` muss leer bleiben außer den beabsichtigten Schlüsseln.
